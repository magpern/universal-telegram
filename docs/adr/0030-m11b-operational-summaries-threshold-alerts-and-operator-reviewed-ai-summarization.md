# ADR-0030 — M11B: Operational Summaries, Threshold Alerts, and Operator-Reviewed AI Summarization

## Status

Proposed

## Context

M11's charter names scheduled summaries, threshold alerts, checkout-failure detection, funnel summaries, error clustering, AI-assisted internal summaries, and destination-specific reporting as its remaining deliverables, all still gated on M09 acceptance per ADR-0029. M09 is technically complete (ADR-0028); **Product Owner acceptance of M09 is pending at this plan's own writing time**, and M11B implementation remains blocked until that acceptance is recorded, exactly as ADR-0029 and M11's charter require — this ADR is a planning-time document, not a claim that the entry condition is already satisfied. M11A already established the pattern for a deterministic, threshold/schedule-driven Telegram-bound aggregate report with a live-revalidated bot+destination target and a suppression-safe, no-flood delivery discipline; M11B's deterministic reports reuse that pattern rather than inventing a second one. M11B's one genuinely new architectural element is an AI-assisted rendering of already-computed aggregate data, structurally prohibited from auto-sending to Telegram or any visitor-facing surface, analogous to but administratively and functionally distinct from M09's AI draft assistant (a different data domain — operational aggregates, not conversation content — and a different retention/ownership model, since there is no conversation row to anchor cleanup) — while deliberately sharing, not duplicating, M09's existing site-wide provider-concurrency admission boundary.

## Decision

1. **Deterministic reporting reuses M11A's target-eligibility and no-flood pattern, unmodified.** Every M11B report/alert destination is validated by the exact eligibility rule M11A's plan already defines (conversation-linked destinations structurally excluded); no new exclusion logic exists.
2. **Threshold alerts default disabled and are cooldown-bounded.** Three fixed alert types (`checkout_failure_count`, `order_failure_spike`, `js_error_spike`), each independently toggleable, each enforcing a fixed 1-hour re-fire cooldown regardless of continued condition persistence — the structural anti-flood guarantee.
3. **Funnel and error-clustering data are aggregate-count-only, by construction.** Funnel stage counts are independent per-event-type counts, never a cross-event join implying unique-visitor conversion; JS-error clustering groups only by M04's existing bounded `error_category` enum, never raw error text — no new field capable of carrying either is introduced anywhere in this ADR's schema.
4. **AI-assisted summarization is operator-triggered, reviews only already-computed aggregate rows, is database-idempotent per summary, is structurally prevented from auto-sending, and shares — never duplicates — M09's site-wide provider-concurrency cap, without adding any class to `AiDraftRepository`'s six-class allow-list.** A new `Automations\Intelligence\SummaryAi*` code path reuses M09's provider abstraction (`AiProviderInterface`, `OpenAiAdapter`, the shared `'ai_provider'` circuit-breaker scope) and, for admission, a new `AI\Provider\ProviderConcurrencyGate` that locks the existing `ai_config` row and sums caller-supplied active-generation counts against M09's unchanged cap of 2 — but the gate itself references no repository class; each domain's own `AiDraftRepository`/`SummaryAiRepository` call stays inside its own already-permitted handler, wired together only by `Core\Plugin.php` (the allow-list's existing, documented composition-root exemption). `AiDraftRepository`'s monolithic `claim_for_generation()` is additively split into `count_active_generating()`/`claim_candidate_row()` to make this possible, with no change to the cap value, lease duration, or compare-and-set guarantee M09 already shipped. M11B's own surface is a new, independent persistence/lifecycle surface (`operational_summary_ai_drafts`, `UNIQUE(summary_run_id)` as its sole per-summary idempotency mechanism, its own lease sweep) — not a reuse of `AI\Draft\AiDraftRepository` or its six-class allow-list, since the data domain (operational aggregates vs. conversation content) and structural guarantee required (never send to Telegram at all vs. never send to a visitor) differ. A structural test extends the `StructuralBoundariesTest` pattern to assert both an access allow-list on the new repository and a zero-reference assertion against `Telegram\Outbound\MessageDispatcher` from within the AI-summary code path.
5. **Four additive tables, `db_version` 24→28.** No existing table (including any M11A table) is altered; the one non-schema change to already-shipped M09 code is the additive split of `AiDraftRepository::claim_for_generation()` into `count_active_generating()`/`claim_candidate_row()` (§WP6), consumed by the new `ProviderConcurrencyGate`, which does not change M09's cap value, lease duration, or failure semantics.

## Alternatives

- *Route M11B's deterministic reports through `DigestEligibility`/`VisitorDigestSweep` directly, adding new categories to the existing digest.* Rejected: M11A's digest is scoped to visitor-activity suppression-replacement specifically; conflating order/error/funnel data into the same window/threshold model would weaken M11A's own frozen suppression-eligibility contract (ADR-0029's explicit non-goal) and couple two independently-toggleable feature sets' cadences together.
- *Reuse `AI\Draft\AiDraftRepository` and its existing six-class allow-list for AI-summary rows.* Rejected: `ai_drafts` rows are conversation-content-derived and follow conversation-lifecycle retention; operational-summary AI drafts have no owning conversation and a different retention trigger (fixed 30-day purge vs. conversation-archival-anchored purge) — forcing them into the same table/allow-list would either weaken M09's existing structural guarantee's precision or require awkward nullable-conversation-id semantics on an already-shipped, frozen table.
- *Give M11B its own independent single-slot concurrency mutex, separate from M09's `ai_config` row.* Rejected: two independent admission mutexes cannot jointly bound total concurrent provider calls — an M09 draft generation and an M11B summary generation could both be admitted simultaneously, each believing itself within its own cap, together exceeding the one real constraint that matters (the provider account's own capacity). Sharing M09's existing cap-of-2 mutex, extended to count both tables, is the only design that actually bounds total site-wide concurrency.
- *Add `ProviderConcurrencyGate` (or `SummaryAiGenerationHandler`) directly to `AiDraftRepository`'s six-class allow-list, and have it call `AiDraftRepository` itself.* Rejected: the allow-list's own point is that a fixed, named set of classes may read/write draft content — adding a class whose actual job is admission counting, not draft review, would blur that guarantee for no necessary reason, since the composition-root closure-injection design (decision 4) achieves the identical outcome without touching the list at all.
- *A per-summary row lock (`SELECT ... FOR UPDATE`) as the AI-summary idempotency mechanism, mirroring M09's conversation-row lock.* Rejected: a row lock only serializes concurrent requests arriving inside the same transaction window — it does not prevent a second row from being created for the same `summary_run_id` by a later, non-overlapping request once the first transaction commits. A database `UNIQUE(summary_run_id)` constraint is the correct, simpler mechanism: it makes a second row for the same summary impossible at the storage layer, permanently, not just under concurrency.
- *Auto-send the AI summary to the same Telegram destination as the deterministic summary, with an operator opt-in setting.* Rejected outright by the charter's own "internal operator material only... never automatically sent" constraint; no configuration path is offered that could weaken this.
- *A single shared destination for all M11B alerts and the summary, rather than independently configurable pairs.* Partially adopted (the three alert types share one destination pair to bound settings-surface growth) but rejected for the Operational Summary itself, which gets its own independent pair — the charter's "destination-specific reporting configuration" deliverable requires genuine per-report configurability where it matters (a daily summary is qualitatively different traffic from a flood-risk alert), while three closely-related alert types sharing one pair is a reasonable, disclosed scope-reduction that does not weaken any privacy or flood-control guarantee.

## Consequences

M11's charter, once M11B is implemented and both M11A and M11B pass the combined validation gate (M11B plan §9), can close as a whole, citing this ADR, ADR-0029, and both closure records. Any later milestone adding a new operational-aggregate report should extend `Automations\Intelligence\*`'s existing pattern (fixed schema row, live-revalidated target, cooldown-gated alert if applicable) rather than introducing a third parallel reporting mechanism alongside M11A's digest and M11B's summary/alert pattern.

## Security and privacy impact

No new event source; every new table's columns are integers, enums, or fixed-vocabulary status strings, **with one explicit exception**: `operational_summary_ai_drafts.body_ciphertext`, which is encrypted, variable-length AI-generated output (`CredentialVault::encrypt()`, mirroring `ai_drafts.body_ciphertext`) — never a public/aggregate field, never surfaced in Diagnostics, audit, or Telegram, and never re-fed into a prompt (it is output only). Every other new column across all four tables is structurally incapable of holding visitor identity, order PII, raw error text, or free text. The AI-summary boundary's prompt *input* is typed to accept only the pre-computed aggregate row object, foreclosing accidental raw-data injection into a prompt by construction (mirrors ADR-0028 decision 2's structural pattern).
