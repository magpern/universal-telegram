# ADR-0006 — Queue Implementation and Failure Semantics

## Status

Accepted

## Context

The master plan requires that Telegram and artificial-intelligence dispatch run through a queue whose own external failures never delay or break an ordinary WordPress request, and, because WooCommerce is a genuinely optional integration under an earlier accepted decision, this queue must function identically whether WooCommerce is present or not. This milestone's own charter requires a durable queue abstraction distinguishing dispatch-path isolation from worker-failure reporting, and explicitly forbids a worker failure ever being silently swallowed and reported as though it had succeeded. The exact installed Action Scheduler library, version 4.1.0, was read directly from source during this plan's own review to establish its integration contract from verified fact rather than assumption: its own bootstrap file self-registers on WordPress's `plugins_loaded` action at priority zero and initializes the highest-registered bundled version at priority one; its own readiness is only guaranteed, via its own `action_scheduler_init` action, once WordPress's own `init` action has fired; and every one of its own procedural functions already self-guards against being called before that point, returning a documented safe sentinel value rather than throwing or fatally erroring. Separately, review of an earlier draft of this same decision identified a serious correctness defect: that draft avoided registering the queue's own worker-execution callback at all while the plugin's schema was unavailable, reasoning that no business logic should run against a broken schema; but because Action Scheduler observes no exception at all when a hook with nothing listening on it fires, that earlier design would have caused an already-scheduled job encountered during any degraded window to be marked successfully complete by Action Scheduler itself, despite never actually running.

## Decision

`woocommerce/action-scheduler`, at version 4.1 or a compatible later version, is bundled as a direct Composer production dependency of this plugin, its bootstrap file required unconditionally as the first executable statement of consequence in the plugin's own main file, immediately after the Composer autoloader is required — a placement that, by the ordinary sequence in which WordPress loads active plugins, inherently satisfies loading the library before its own priority-zero self-registration, without requiring any separate timing coordination. A job is represented by an immutable envelope carrying a stable identifier generated once and threaded unchanged through every retry attempt of that same logical job, together with a payload subject to a fail-closed classification policy enforced in the envelope's own constructor: every payload field must carry an explicit classification, and any field left unclassified or classified as sensitive or secret causes the envelope's own construction to fail immediately, to the calling code, rather than allowing sensitive data to ever reach Action Scheduler's own persisted, unencrypted storage. Dispatching a job never blocks or breaks the request that dispatches it: the dispatcher returns a typed result rather than nothing at all, and never throws under any circumstance, treating both a caught exception and a returned action identifier of zero, a documented failure signal the library's own functions return rather than throwing in several of their own internal failure paths, identically as dispatch failure. A single callback, always registered on every request regardless of the plugin's own schema availability, handles job execution; it checks the plugin's own schema-availability state as the very first thing it does, before ever looking up or invoking any job handler, and if the schema is unavailable, it does not execute any business logic at all, instead raising a typed exception representing that specific condition and passing it through exactly the same failure-handling sequence used for any other worker-side exception. That sequence performs four independently guarded steps — recording an attempt-failure entry, consulting the generic retry policy, either scheduling the next attempt or recording a terminal failure, and finally always rethrowing the original exception — structured so that a failure inside any one step, including a failure to record anything at all because the plugin's own audit storage happens to be the very thing that is unavailable, can never suppress the steps that follow it, and so that Action Scheduler's own bookkeeping for the attempt in question is always, correctly, marked failed, never successful, regardless of what caused that failure. The retry policy itself is entirely generic — a bounded maximum number of attempts, exponential backoff with jitter, and no awareness of any specific external provider's own failure semantics — with deterministic clock and jitter seams provided specifically so its own timing behavior can be tested exactly, not merely approximately. An internal registry, owned by the plugin's own composition root and never exposed as a public extension point, maps a job type to its handler; this milestone registers exactly one real handler through it, the bounded diagnostic self-test described elsewhere in this plan, which is the concrete proof that the registry, the dispatcher, and the worker-execution callback function correctly together, end to end.

## Alternatives

Continuing to rely on WooCommerce's own bundled copy of the library rather than bundling it directly — rejected, since this would silently remove queueing entirely from any WordPress-only installation, directly contradicting the requirement that this plugin's core Telegram functionality work identically whether WooCommerce is present or not. Building queueing on raw WordPress cron together with a custom-built circuit breaker, rather than on this library — rejected, since raw cron carries no native retry, backoff, or dead-letter primitive of its own, and reimplementing what this library already provides, reliably, would be exactly the kind of premature bespoke complexity this milestone's own reliability requirements argue against. Trusting every future caller to redact a job's own payload correctly before dispatching it, rather than enforcing this centrally inside the envelope's own construction — rejected, since centralizing this single check removes any reliance on caller discipline entirely. Recording a worker failure through both the worker's own failure-handling sequence and Action Scheduler's own separate failed-action hook — rejected, in favor of a single recording path, which avoids the risk of duplicate records by construction rather than needing to reconcile them afterward. Leaving the worker-execution callback unregistered while the plugin's schema is unavailable, as an earlier draft of this same decision proposed — rejected, for the correctness reason described in this decision's own context above: doing so allows an already-scheduled action to be silently marked successful by Action Scheduler itself without ever actually executing, which directly contradicts this milestone's own explicit prohibition on a worker failure ever being reported as though it had succeeded.

## Consequences

Every later milestone that dispatches a genuine job against an external provider registers its own handler through this same internal registry and supplies its own explicit payload classification map; a handler attempting to pass a secret-classified field through it fails loudly during that milestone's own development, not silently, later, in production. Bundling this library directly, rather than relying on WooCommerce's own copy, is a deliberate, verified departure from every sibling plugin's own precedent in this Product Owner's fleet, justified specifically by this plugin's own WooCommerce-optional requirement. Every future service that touches this plugin's own schema must follow the same schema-availability-checked pattern this decision establishes for the queue itself, rather than relying on selective construction inside the composition root to avoid touching a broken schema.

## Security and privacy impact

The fail-closed payload-classification policy is itself a security boundary: it structurally prevents sensitive data, whether a credential or genuine message content, from ever being written into Action Scheduler's own unencrypted, comparatively long-retained storage, regardless of what a future handler's own author might otherwise be tempted to pass through it.

## Affected Documents/Milestones

Milestone M01, whose Telegram-dispatch job is the first genuine handler registered against this foundation and the first to add its own provider-specific retry classification on top of it; milestone M09, in the same relationship for artificial-intelligence provider dispatch; the earlier accepted decision governing this milestone's overall release-boundary sequencing, whose own scope for milestone M12's reliability-mechanism validation remains limited to this queue's Telegram-transport mechanisms specifically, unchanged by this decision.

## Compatibility/Migration Impact

None. No code of any kind exists in this repository yet; adding this library is the introduction of a new dependency, not a change to an existing one.
