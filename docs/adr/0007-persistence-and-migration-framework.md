# ADR-0007 — Persistence and Migration Framework

## Status

Accepted

## Context

This milestone's own charter requires a database schema migration framework covering only the schema this milestone genuinely needs, with dependable upgrade behavior. Review of two successive earlier drafts of this decision identified three distinct correctness gaps that needed resolving before this decision could be accepted: first, a migration lock implemented as a separate read followed by a separate write is not genuinely atomic, and is vulnerable to a specific race in which a delayed original lock holder's own release could destroy a legitimate replacement holder's lock; second, prescribing a specific data-definition clause for adding a column in some future migration step as a universal strategy assumes a level of database-version support that is not guaranteed across every database version a WordPress installation may run; and third, a migration failure discovered outside of plugin activation — during an ordinary frontend request, for instance, or during a job Action Scheduler itself is driving — had no defined behavior short of risking that request crashing entirely, which would directly contradict this same milestone's own architectural constraint that external and internal failures alike must never break ordinary WordPress operation.

## Decision

Schema changes are implemented as numbered, ordered steps, each executing raw data-definition statements directly rather than through WordPress core's own `dbDelta` helper function, whose own documented limitation of silently dropping certain composite or prefix-length index declarations this Product Owner's own fleet has already encountered in practice, and whose recurrence this plugin's own anticipated schema growth makes a genuine, not merely theoretical, risk. Table creation uses a data-definition clause supported extremely broadly across the database versions a WordPress installation may run, making a given step safe to re-run in full after any partial failure; any future step that instead needs to add a column to an existing table does not rely on an equivalent clause for that operation, since that specific clause's own support is not guaranteed as broadly, and instead first inspects the database's own information schema to determine whether the column already exists, issuing a plain, universally supported statement to add it only when it is genuinely absent. Every step is paired with its own postcondition-verification method, re-querying the database's own information schema after the step's own statements run to confirm the resulting schema genuinely matches what the step intended, rather than relying solely on the absence of a reported database error, which alone would be insufficient for any step containing more than one statement, since each such statement commits individually rather than as part of one atomic transaction. The schema-version marker, itself deliberately kept separate from the plugin's own general settings storage, advances only immediately after both a step's own statements and its own postcondition check succeed, never partially. Concurrent migration attempts are coordinated through a lock whose every single state transition — a fresh acquisition, a stale-lock reclamation, and a release — is expressed as one genuinely atomic conditional SQL statement, never a separate read followed by a separate write: a fresh acquisition relies on a unique database constraint to guarantee only one such statement can ever succeed; a stale-lock reclamation is expressed as a single conditional update that only succeeds if the lock's contents still match exactly what was read moments before; and a release is expressed as a single conditional delete matching both the lock's own name and its own exact current contents, which is a safe, silent no-op rather than an error whenever those contents no longer match what the releasing process itself once held, precisely because some other process has since reclaimed the lock as stale. Every one of these direct SQL writes is followed immediately by an explicit invalidation of WordPress's own options cache for that specific value, since these writes bypass the caching layer WordPress's own option-reading functions otherwise rely on.

A migration failure discovered outside of plugin activation — during any ordinary post-activation request of any kind — is caught by the plugin's own composition root at the same point it attempts the migration, marking a dedicated schema-availability service unavailable for the remainder of that one request only, a state recomputed fresh on every subsequent request rather than persisted anywhere, so that recovery from a transient cause is automatic. Rather than selectively deciding, inside the composition root itself, which services to construct based on this availability state — an approach an earlier draft of this same decision took, and which produced a related but distinct correctness defect in the queue's own worker-execution behavior, described in the sibling decision governing queue implementation — every service this milestone introduces is always constructed and always wired, in every request, regardless of schema availability; instead, each individual operation that genuinely touches the database checks this same availability state, or is itself defensively guarded, at its own specific point of use. Wherever a degraded-schema condition is ever reported to any surface outside the plugin's own internal state, only a small, fixed, stable failure code is ever used — the underlying raw database error itself is never rendered to an administrator, never shown on any diagnostic surface, and never written to any log this plugin itself controls. Network-wide activation, across an entire WordPress multisite network at once, is explicitly refused outright rather than partially supported: the plugin's own activation routine inspects the flag WordPress itself provides indicating a network-wide activation and, when present, halts with a clear explanation and performs no schema provisioning of any kind; activation for a single site within a multisite network remains fully supported and behaves identically to a non-multisite installation. The plugin's own tables remain entirely independent of any table any other WordPress dependency, including the queue library covered by the sibling decision on queue implementation, itself owns.

## Alternatives

A migration lock released by first reading its current value and then separately deleting it — rejected, since this is precisely the non-atomic pattern whose race this decision exists to close. Prescribing a column-addition clause as a universal strategy for every future migration step, on the assumption that any database version a WordPress installation might run would support it — rejected, since that specific clause's own support is not, in fact, guaranteed across every such version. Allowing a migration failure discovered outside activation to propagate as an uncaught exception — rejected, since this would crash the very request that discovered it, directly contradicting this plugin's own architectural constraint that failures, whether external or internal to the plugin's own schema layer, must never break ordinary WordPress operation. Selectively constructing services inside the composition root based on schema availability, rather than always constructing every service and guarding individual database-touching operations at their own point of use — rejected, since selective construction is precisely what allowed a WordPress hook callback to end up silently unregistered in an earlier draft, which is the defect the sibling decision on queue implementation exists to correct. Partial or best-effort support for network-wide multisite activation — rejected, in favor of an unambiguous refusal, since a partial or unclear state is worse than a clear one.

## Consequences

Every later milestone that adds its own schema extends this same migration framework with its own idempotent, information-schema-guarded, postcondition-verified steps, and any schema-dependent service any later milestone introduces must follow the same availability-checked pattern this decision establishes, rather than relying on selective construction to avoid a broken schema.

## Security and privacy impact

None beyond what the sibling decision governing audit logging and privacy classification already covers for this plugin's own audit table's content. The degraded-mode redaction discipline this decision establishes prevents a raw database error, which could in principle echo back some fragment of internal schema detail, from ever reaching any user-facing or logged surface.

## Affected Documents/Milestones

Every later milestone that adds its own schema to this plugin; the sibling decision governing queue implementation, whose own worker-execution correction directly depends on the schema-availability service this decision introduces.

## Compatibility/Migration Impact

None. No code or schema of any kind exists in this repository yet.
