# M04 — Visitor and Browser Events — Definitive Implementation Plan (v1)

Status: Frozen — implementation authorized. This document is self-contained: it does not require a reader to consult any earlier conversation draft or planning-session transcript.

Implements: `docs/milestones/m04-visitor-and-browser-events.md`. Extends the M02-frozen event system (ADR-0015, ADR-0016, ADR-0017) with a third, anonymous, browser-originated event source (`EventSource::VISITOR`), gated on nothing (always-on core scope) plus a WooCommerce-gated subset (reusing the M03/ADR-0018 `WooCommerceSupport::is_active()` pattern). Proposes ADR-0019, full text included below (§13) and materialized alongside this plan under `docs/adr/`.

## 1. Charter and ADR references

Charter: `docs/milestones/m04-visitor-and-browser-events.md` (depends only on M02, closed PASS). Governing ADRs reused unmodified: ADR-0005 (Events is the owning top-level boundary; visitor/browser events are a subdomain, not a new boundary), ADR-0009 (fail-closed four-level classification), ADR-0011 (M04 is in the M00–M09 range: no Vlad manual-acceptance gate; required evidence is frozen plan + code review + automated tests + green CI), ADR-0015 (`EventIdentity`, `EventEnvelope`, `Registry`, `EventEmitter` façade, sole emission surface `universal_telegram_emit_event()`), ADR-0016 (rule engine: flat AND-only conditions over `Registry::allowed_variable_fields_for()`), ADR-0017 (history projection fields must be `Classification::PUBLIC`), ADR-0018 (M03's WooCommerce catalog — the boundary M04 must not duplicate).

One new ADR is required: ADR-0019, because this milestone changes a public contract (`universal_telegram_emit_event()`'s signature) and establishes a new security boundary (an unauthenticated public REST endpoint). Full text in §13.

`HEAD == origin/main == 77dc0a5` (M03 closure commit), working tree clean. Confirmed by direct read: `Events\Registry`, `EventEnvelope`, `EventEmitter`, `EventDispatcher`, `Core\Configuration\Settings` (current keys, all `defaults()`/`sanitize()` extended additively by every milestone so far). ## 3. Scope and exclusions

In scope, per charter: tracking client; page/product views; navigation; configurable click events; search events; JS error reporting; consent integration; bot filtering; batching/sampling. Out of scope, per charter and per the agreed boundaries: any chat/AI (M06/M09+); any event duplicating a M03 `woocommerce.*` confirmed server event; cookies; fingerprinting; persistent visitor identity; query strings, fragments, form values, referrers, raw user-agent, raw error text/stack traces, search terms (raw or hashed), client error location (filename/line/column, raw or hashed), or any other PII; "buy/place-order intent" (no reliable, privacy-safe browser signal exists — explicitly declared not implemented, not deferred silently); block-based WooCommerce add-to-cart interception (no verified public WooCommerce block browser-event API — see §4.6); funnel/abandonment signals beyond what the six core types already provide; any new DB table; any new queue job type; any change to `EventDispatcher`'s synchronous contract, `Registry`, `EventEnvelope`, `EventIdentity`, or the rule/template engine.

## 4. Architectural decisions

### 4.1 EventSource threading (public-contract change, additive/backward-compatible)

`universal-telegram-functions.php`: `universal_telegram_emit_event( string $event_type, array $data, string $idempotency_key, EventSource $source = EventSource::WORDPRESS_CORE ): void`. `EventEmitter::emit()` and `build_envelope()` gain the same optional parameter, threaded straight through to `new EventEnvelope(...)`. No existing call site changes behavior (all omit the 4th argument, default preserves current output). This is the only modification to M02 infrastructure in this milestone; every M03 call site is unaffected.

### 4.2 Event catalog (9 types, all `EventSource::VISITOR`, `schema_version = 1`, registered on the existing `universal_telegram_register_event_types` hook, priority 20)

Registered by two new emitter classes mirroring the M03 pattern: `Events\Visitor\VisitorEventCatalog` (6 always-on types) and `Integrations\WooCommerce\Visitor\VisitorCommerceEventCatalog` (3 types, registered only when `WooCommerceSupport::is_active()`).

`context.visit_ref` is **not** an event field anywhere in this catalog. It exists only transiently in the browser's request body and as raw input to the idempotency-key string passed to `universal_telegram_emit_event()`; it is never placed into `actor`/`subject`/`context`/`payload`, never classified, never persisted, never reaches `EventEnvelope`, `event_history`, an audit entry, a rule condition, a template token, or any admin display.

|---|---|---|---|---|
| `visitor.session_started` | *(none)* | *(none)* | *(none)* | `'visit:' . visit_ref` (client-supplied `visit_ref`, used only as key input) |
| `visitor.page_viewed` | `subject.path` (PUBLIC, leading-slash, ≤190B, no query/fragment), `subject.page_type` (PUBLIC, enum: `home\|singular\|search\|archive\|other`) | `subject.path`, `subject.page_type` | `subject.path`, `subject.page_type` | client-supplied UUIDv4, `'event:' . event_uuid` |

#### Overlap avoidance with M03

`visitor.add_to_cart_intent`/`checkout_started_intent` are distinct in type string, `EventSource` (`VISITOR` vs `WOOCOMMERCE`), and `event_id` from `woocommerce.cart_item_added`/order events. No correlation is attempted or stored between an intent event and its possible M03 confirmation — stated as an accepted limitation, not a gap to close later.

### 4.3 Privacy and consent model

- `Settings::defaults()` gains: `visitor_tracking_enabled` (bool, default `false`), one bool per event family (`visitor_family_page_views`, `_navigation`, `_search`, `_clicks`, `_errors`, `_commerce`, default `false` each), `visitor_consent_mode` (enum `required|disabled`, default `required`), `visitor_sampling_percent` (int 1–100, default 100), `visitor_click_target_allowlist` (array of ≤8 string keys, default empty), `visitor_exclude_administrators` (bool, default `true`). Tracking is opt-in at two levels: the master switch and at least one family toggle, both off by default — matching master-plan §15's "no tracking enabled automatically."
- Consent mode `required`: the tracker checks, before any collection, for a boolean JS global `window.universalTelegramConsent === true`, expected to be set by the site's own consent tooling. This is a **client-side suppression mechanism only**. The unauthenticated endpoint has no way to verify that consent was actually granted by a real visitor — a non-browser client, or a visitor with developer tools open, can submit requests regardless of this flag's true state. The plan does not claim server-enforced consent and does not claim every accepted event is consented; the endpoint's privacy guarantee rests entirely on what data it is structurally incapable of accepting (§4.2), never on trusting the consent signal. Settings-page copy states this explicitly: *"This checks a signal from your consent tool before collecting data in the visitor's browser. It cannot be verified by the server and is not a substitute for your own compliance review."* Mode `disabled` skips the check entirely (site has no consent requirement or handles it out of band). The plugin implements no consent-management UI of its own.
- `visit_ref`: a 16-byte random hex string generated client-side via `crypto.getRandomValues()` the first time the tracker runs with no existing value in `sessionStorage`, stored under one `sessionStorage` key, and reused unchanged across every reload and same-tab navigation for the remainder of that tab's browser session (`sessionStorage` survives reloads by design — it is cleared only when the tab or browser session ends). A new tab, or a tab whose session storage was cleared, gets a new `visit_ref` and is an independent visit. Not a cookie, not sent to any third party, never persisted server-side in any form — it is only ever used as one-shot idempotency-key input (§4.2), and `EventHistoryRepository` persists only the derived `event_id`, never the `idempotency_key` itself.
- Retention: reuses the existing `event_retention_days` setting (default 90) — `visitor.*` history rows are deleted by the same existing `RetentionCleanup` pass as every other event type. No new retention field.
- Never collected, by construction (endpoint rejects the field outright if present): IP address, raw user-agent string, cookies, `localStorage`/other storage contents, form values, query strings, fragments, referrer URLs, raw error message/stack trace, search terms or any hash/derivative of them, client error file/line/column or any hash/derivative of them, user ID, email, name, or any other free-text field.

### 4.4 Browser-to-server delivery boundary

- Route: `POST universal-telegram/v1/visitor-events`, registered unconditionally on `rest_api_init` (mirroring `WebhookController`'s pattern), `permission_callback => '__return_true'`; authenticity/abuse controls live inside the callback, not in WP-REST's auth layer.
- Same-origin check: the callback requires either an `Origin` header matching `home_url()`'s scheme+host, or (fallback, since some browsers omit `Origin` on same-origin POSTs) a `Referer` header whose scheme+host matches. Missing or mismatched → 400. This check is **browser-CSRF friction only, not authentication** — both headers are trivially forgeable by any non-browser client, so the endpoint is treated throughout this plan as attacker-writable regardless of these checks. No WP nonce is used, because a nonce baked into cached HTML would be stale or missing entirely under full-page caching, which the charter forbids depending on.
- Request body: JSON, ≤8192 bytes, checked via `Content-Length`/actual byte count **before** `json_decode()` (413 if exceeded, mirroring `WebhookController`). Shape: `{"v":1,"visit":"<32 lower-hex>","events":[{"uuid":"<uuid4>","type":"<short-code>","data":{...}}, ...]}`, 1–10 events per batch. Short-code table (not full dot-namespaced strings, to bound payload size): `ss→session_started`, `pv→page_viewed`, `nv→navigation`, `sr→search_performed`, `ck→click`, `je→javascript_error`, `pd→product_viewed`, `ac→add_to_cart_intent`, `cs→checkout_started_intent`. `data` is a flat object, ≤6 keys, each scalar value ≤190 bytes; any unlisted key or nested array/object → 400. Unknown top-level key, unknown `type`, malformed `visit`/`uuid` shape → 400.
- Rate limiting and abuse hard cap — two independent, non-bypassable layers, both reusing `Telegram\Reliability\RateLimiter` unchanged, two new `scope_type` values on the existing table:
  - `visitor_ingest` (per-client fairness bucket; friction, not a security boundary — a determined attacker rotating IP/UA/`visit` values can obtain a fresh bucket). `scope_id` is derived via `hash_hmac('sha256', ip . "\x1f" . user_agent . "\x1f" . current UTC date, $secret)`, truncated to a 31-bit integer, where `$secret` is a 32-byte value generated once via `random_bytes()` on first use and stored in a non-autoloaded option (`universal_telegram_visitor_rate_limit_secret`), never exposed in any UI or export. This is deliberately **transient security processing, not visitor tracking data** — it is never placed in an `EventEnvelope`, never classified under `Privacy\Classification`, and never reversible back to the raw IP or UA even by someone with database access, since the key is never persisted alongside its HMAC secret in a way that reconstructs the input; the raw IP/UA are read from the request only for the duration of this one calculation and immediately discarded. Capacity 30, refill 0.5/s.
  - `visitor_site` (global bucket, `scope_id = 0`, not derived from any client-supplied value, so it cannot be evaded by forging headers, rotating IPs, or generating fresh `visit`/`uuid` values). This is the **actual hard cap** protecting `event_history` write volume and rule/queue evaluation pressure: capacity 300, refill 5/s, values intentionally conservative and administrator-tunable only via a future ADR (not exposed as a self-service setting in M04, to avoid an administrator accidentally disabling the plugin's own DoS protection).
  - Either bucket exhausted → 429.
- Uniform response: every accepted-but-suppressed case (tracking disabled, family disabled, consent flag false, bot user-agent detected, sampled out) returns the same `202 Accepted` with an empty body as a genuinely-accepted request — no differential response exists that would let a caller distinguish "collected" from "silently dropped." Genuine schema unavailability → 503.
- Cache/CDN compatibility: the endpoint is never behind the WordPress page cache (REST routes bypass it); the inline tracker configuration (§4.6) is static per-URL and safe to be baked into any cached HTML variant, since the endpoint itself re-validates every setting live on each request.
- Delivery strategy: `navigator.sendBeacon()` on `visibilitychange`/`pagehide` (survives navigation away), `fetch(url, {method:'POST', keepalive:true})` otherwise. Every call site wrapped in `try/catch`; the tracker never throws, never blocks rendering, never delays navigation, and has no synchronous DOM/CSS dependency.
- Bot filtering: `Events\Visitor\BotFilter` reads the raw `User-Agent` request header transiently (never persisted, never placed in any event field, never part of the HMAC bucket's stored output) and rejects known crawler/headless substrings and empty UAs before any envelope is built.
- Sampling: `Events\Visitor\Sampler` computes `sha256(event_uuid)` → first 4 hex chars as an integer mod 100; admits if `< visitor_sampling_percent`. `session_started` and `javascript_error` are exempt (always admitted) since they are the lowest-volume, highest-diagnostic-value types.

### 4.5 Identity, duplicates, and volume guarantees (honest statement)

- One `session_started` per tab session: the client emits it only when `sessionStorage` had no existing `visit_ref` (i.e. a genuinely new tab session), and because `visit_ref` is stable across reloads, a reload does **not** produce a new session or a new `session_started` event — a reload is simply another `page_viewed` under the same, unchanged `visit_ref`. Server-side, the idempotency key `'visit:' . visit_ref` also collapses any accidental resend to one `event_history` row, as a backstop.
- Back/forward navigation and duplicate beacon delivery (network retry, double `sendBeacon`) are deduplicated at the `event_id` level (`EventIdentity::derive()` is deterministic on `event_type + schema_version + idempotency_key`; the client-generated `uuid` is the idempotency key and is reused unchanged on any retry of the same logical event, so a resend with the same `uuid` collapses to one `event_history` row via the existing `INSERT IGNORE`). A genuinely repeated user action (two separate clicks) gets two separate UUIDs and is recorded twice — this is correct, not a duplicate.
- Multiple tabs are multiple independent visits (`visit_ref` is tab-scoped `sessionStorage`), not one visitor — no unique-visitor count is claimed anywhere.
- Rapid repeated errors: capped to at most 5 `javascript_error` events per tab session, via a simple client-side counter reset only when a new `visit_ref` is generated — since no location data is collected (§4.2), no per-location distinctness is possible or attempted; the cap is a flat volume bound, not a deduplication mechanism.
- Guarantee statement: at-least-once recording within the event-retention window, deduplicated by `event_id`; not exactly-once delivery, not unique-visitor counting, not guaranteed completeness against a determined adversary or ad/tracker-blocking software, and not a guarantee that every recorded event reflects a consenting visitor (§4.3).

### 4.6 WooCommerce/browser interaction coverage

Gated entirely on `WooCommerceSupport::is_active()` at emitter-wiring time in `Core\Plugin::init()`, identical to M03's existing conditional block — when WooCommerce is inactive, the three types simply never register and the tracker's config omits the `commerce` capability flag, so no commerce-related client-side code runs.

- `visitor.product_viewed`: fires from `PageContext` when `is_product()` is true (server-rendered page-type detection reused from the page-view payload, not a JS product-detection heuristic); `subject.product_id` validated against `wc_get_product()` server-side — a forged/nonexistent id is rejected 400, never recorded.
- `visitor.add_to_cart_intent` — **classic checkout only**: a `document` click listener matching `.single_add_to_cart_button, .add_to_cart_button` on classic (shortcode-rendered) product/shop pages. No public, verifiable WooCommerce block browser-event API was confirmed available for the block-based cart/checkout flow within this plan's scope; rather than infer coverage from undocumented block markup or internal CSS class names, block add-to-cart is explicitly and intentionally **unsupported in M04** and documented as such. If a genuine public WooCommerce block event API is confirmed in a future milestone, extending coverage to it is a candidate for that milestone's own charter, not a silent addition here. Fail-silent by design where a theme replaces even the supported classic markup: no event rather than a wrong one.
- `visitor.checkout_started_intent` — **page-entry intent, not checkout progress**: fires once per visit when `PageContext` reports `is_checkout()` true. This is a server-rendered WordPress conditional that is true for both classic and block checkout pages equally, so it requires no CSS-selector inference; it signals only that the visitor's browser rendered the checkout page, not that any checkout step, field, or payment action occurred.

## 7. Test/CI impact

WP-only and WC-present integration configs both apply (visitor tracking touches product/checkout pages). No JS build tooling, package manager, or third-party JS dependency is introduced. The tracker's structural properties (file size ≤8192 bytes, ASCII/UTF-8 validity, absence of a fixed disallowed-token list such as `eval(`, `document.cookie =`, `localStorage`, `XMLHttpRequest`, raw `http://`/`https://` literals) remain as a supplementary PHP unit guard, but are not the primary evidence for the tracker's correctness. Primary evidence is a minimal, dependency-free behavioural test suite run via Node's own built-in test runner (`node --test`, zero npm dependencies, no `package.json`), invoked through one new thin Docker wrapper script, `bin/docker/test-js.sh`, following the repository's existing one-script-per-check convention (`bin/docker/phpcs.sh`, `test-unit.sh`, etc.) rather than assuming Node is preinstalled on any CI runner. `tests/js/visitor-tracker.test.mjs` stubs the minimal browser globals the tracker touches (`fetch`, `navigator.sendBeacon`, `sessionStorage`, `window`, `document.addEventListener`) and asserts: constructed event objects match the short-code schema (§4.4); the consent gate suppresses every outbound call when `window.universalTelegramConsent` is unset under `required` mode; a simulated retry of one logical event reuses the same `uuid` rather than generating a new one; a simulated same-tab navigation records one `from_path`/`to_path` pair per transition; and a 6th simulated error after 5 produces no further outbound call. This is a genuinely new, minimal CI job — narrowly scoped to this one behavioural suite, not general JS tooling.

## 10. Risks and mitigations

Public endpoint as DoS surface, including forged headers or rotated `visit`/`uuid` values → the `visitor_site` global bucket is keyed independently of any client-supplied value and cannot be evaded this way; `visitor_ingest`'s HMAC-keyed daily bucket adds fairness friction without becoming a stored, reversible visitor identifier. Forged or absent consent flag → accepted and documented as a client-side-only, non-verifiable signal in the settings copy, ADR-0019, and closure evidence; the endpoint's actual privacy guarantee is structural (§4.2), not consent-dependent, so the worst outcome of a forged flag is bounded, non-personal event rows, never a privacy breach. Theme markup drift breaks the classic add-to-cart selector → fail-silent by design, documented limitation. Block-based add-to-cart coverage gap → explicitly documented as unsupported in M04 rather than approximated via unverified selectors. Stale cached HTML with an outdated tracker config → server re-validates every setting per-request.

## 11. Out of scope

Buy/place-order intent; block-based WooCommerce add-to-cart interception; funnel/abandonment signals beyond the six core types; any correlation between an intent event and its M03 confirmation; any consent-management UI or server-side consent verification; any new DB table; any change to `Registry`/`EventEnvelope`/`EventIdentity`/`EventDispatcher`/rule engine beyond §4.1; any JS package manager, bundler, transpiler, or third-party JS dependency (the one new CI job uses only Node's own built-in test runner via a Docker wrapper script, per §7); a new plugin capability constant; chat/AI milestones.

## 13. Proposed ADR text

### ADR-0019: Visitor Event Source Threading and Browser Ingestion Boundary

#### Status

Proposed

#### Context

M02 (ADR-0015) established `universal_telegram_emit_event( string $event_type, array $data, string $idempotency_key ): void` as the sole sanctioned emission surface, and `Events\EventSource` as a closed enum identifying the emitting subsystem on every recorded event. `EventSource::VISITOR` was reserved at M02 for exactly this milestone but is unreachable: `Events\EventEmitter::build_envelope()` hard-codes `EventSource::WORDPRESS_CORE` on every call, with no parameter to override it. M04 (`docs/milestones/m04-visitor-and-browser-events.md`) requires capturing anonymous browser-originated events — page views, navigation, search, clicks, JS errors, and (WooCommerce-gated) product-view and classic add-to-cart intent signals — attributed as `VISITOR`-sourced, and requires a public, unauthenticated ingestion boundary through which an anonymous browser can reach that emission surface, since no such boundary exists in the plugin today (the only prior public REST route, `Telegram\Inbound\WebhookController`, is secret-token-authenticated and not reusable for anonymous visitors, who cannot hold a secret).

#### Decision

1. `universal_telegram_emit_event()` gains a fourth, optional parameter: `EventSource $source = EventSource::WORDPRESS_CORE`, threaded unchanged through `EventEmitter::emit()` and `build_envelope()` into `EventEnvelope`'s existing constructor parameter. Every existing three-argument call site is unaffected; behavior for those call sites is unchanged. An unrecognised source is impossible by construction (PHP enum typing), so no new failure mode is introduced.
2. A new public REST route, `POST universal-telegram/v1/visitor-events`, is added, gated on a same-origin `Origin`/`Referer` header check (browser-CSRF friction only, not authentication — the endpoint is treated as writable by any non-browser client that forges these headers), a two-tier rate limiter reusing `Telegram\Reliability\RateLimiter` (a per-client HMAC-keyed daily bucket for fairness, and a global site-wide bucket, keyed independently of any client-supplied value, as the actual non-bypassable hard cap on write volume), a strict allow-listed short-code event schema, and a uniform `202 Accepted` response for every accepted-or-silently-dropped case. It accepts only the nine registered `visitor.*` event types and forwards each, after validation, sampling, and bot-filtering, to `universal_telegram_emit_event()` with `EventSource::VISITOR`.
3. No WordPress nonce is used for this route, because a nonce embedded in full-page-cached HTML would be stale or absent for any cached page view — a hard constraint from the M04 charter.
4. The catalog's fields exclude any per-visitor correlation token (`visit_ref` is used only as transient idempotency-key input, never as an event field), any search term or derivative, and any client error location or derivative, so that the endpoint's privacy guarantee does not depend on trusting an unverifiable consent signal (§4.3 of the M04 plan).

#### Alternatives

- Add a dedicated `EventSource::VISITOR`-only emission function instead of extending `universal_telegram_emit_event()`. Rejected: this would create a second emission path, contradicting ADR-0015's "the sole sanctioned emission surface" guarantee, and would require the same envelope-construction logic to exist twice.
- Use a WordPress nonce for the ingestion endpoint, refreshed via a short-lived AJAX call before every batch. Rejected: adds a synchronous round-trip before any telemetry can be sent, defeating the "no telemetry-induced frontend delay" constraint, and still fails for the very first page view under a full-page cache.
- Route browser events through the existing Telegram webhook controller's pattern (secret-token-per-installation). Rejected: a secret embedded in publicly-served frontend JavaScript is not a secret; this would provide no real authentication while adding false confidence.
- Rely solely on the per-client rate-limit bucket, with no site-wide bucket. Rejected: a per-client bucket keyed even partly on client-supplied or client-observable values can be evaded by an attacker willing to vary IP or generate fresh identifiers per request; only a bucket keyed independently of any client-supplied value provides a genuine, non-bypassable hard cap.

#### Consequences

`EventEmitter`'s public signature grows by one optional parameter — a strictly additive, non-breaking change. A new top-level attack surface (an unauthenticated public endpoint) exists in the plugin for the first time; its blast radius is bounded to inserting rate-limited, schema-constrained, non-PII rows into `event_history` and triggering existing notification rules — never database, filesystem, or credential access. `EventSource::VISITOR` becomes a real, populated value across `event_history.source` for the first time. Administrators must understand, per the settings-page copy, that the `visitor_consent_mode` signal is advisory and client-side only, not a compliance guarantee.

#### Security and privacy impact

The endpoint accepts no field capable of carrying PII (§4.2–§4.3 of the M04 plan): every accepted field is either a bounded enum, a validated numeric ID, or absent entirely. Classification enforcement (ADR-0009) and PUBLIC-only history projection (ADR-0017) apply unchanged and unweakened to every visitor event type. The per-client rate-limit bucket key is an HMAC of IP+UA+day keyed with a per-install secret never exposed outside the plugin's own storage, itself never reversible to the raw IP or UA and never treated as visitor-tracking data — it is transient security processing outside the event/classification model entirely. No cookie, no persistent identifier, and no cross-session or cross-device tracking is introduced. Consent enforcement is explicitly non-verifiable server-side; this ADR does not claim otherwise, and the plan's privacy guarantee is structural (what the schema cannot accept), not consent-dependent.

#### Affected Documents/Milestones

`docs/milestones/m04-visitor-and-browser-events.md` (implements this ADR); `docs/ARCHITECTURE.md` (Events boundary description gains the visitor/browser subdomain, per its own existing statement that M04 is such a subdomain); no other milestone charter or frozen plan is altered.

#### Compatibility/Migration Impact

No database schema change; `db_version` remains `10`. No breaking change to any existing call site of `universal_telegram_emit_event()`. Plugin version moves `0.2.0 → 0.3.0` per `docs/ARCHITECTURE.md`'s existing minor-bump-per-capability-class convention.
