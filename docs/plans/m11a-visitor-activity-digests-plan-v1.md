## 2. M11A boundary and scope-change authorization

M11's charter (`docs/milestones/m11-digests-and-operational-intelligence.md`) currently treats digests as one undivided milestone dependent on M02/M03/M04/M09, explicitly because "AI-assisted internal summaries is one of its deliverables... not split into an AI and a non-AI portion." Executing a non-AI-only visitor-digest slice first is therefore a **milestone-boundary change** under `docs/governance.md`'s scope-change rule ("an ADR if the change touches... a milestone boundary"). **ADR-0029** (full text §10) records this split. It does not reopen M09 (still pending Product Owner acceptance — irrelevant to this non-AI slice, since this slice's only M09 dependency was for the AI-summary deliverable it explicitly excludes) and does not start M10.

**In scope (M11A):** scheduled visitor-activity digests; threshold/timeout batching; a bot+destination delivery target; suppression of direct per-event Telegram delivery for low-severity visitor events; the JavaScript-error decision below.

**Explicitly deferred, unstarted:** AI-assisted internal summaries (remains M11, blocked on M09 acceptance); checkout-failure detection, funnel summaries, error clustering, destination-specific reporting beyond the one visitor-digest target (remain M11, unscheduled); M10 controlled AI responses (unstarted); M12 (unstarted).

## 3. Current-to-new delivery behavior

**Digest-eligible M04 event types** (all `EventSource::VISITOR`, per ADR-0019/M04 plan §4.2), mapped to four fixed categories:

| Category | Event types |
|---|---|
| `page_views` | `visitor.page_viewed`, `visitor.navigation` |
| `product_views` | `visitor.product_viewed` (WC-gated) |
| `search` | `visitor.search_performed` |
| `cart_intent` | `visitor.add_to_cart_intent`, `visitor.checkout_started_intent` (WC-gated) |

`visitor.click` is **not** part of this catalogue: click collection was disabled entirely by hotfix PR #25 (the baseline commit itself, §1) and this plan does not reintroduce it as a planned event source, active or dormant — the four-category table above is the complete digest-eligible catalogue. `visitor.session_started` is **excluded from the digest** entirely (zero-payload, no useful aggregate beyond a raw event count already visible in Diagnostics' existing `visitor_events_recorded_24h`) but remains digest-*eligible* for suppression purposes (see below) since it is still routine, always-on, low-severity traffic. `visitor.javascript_error` is excluded from both digest content and suppression — see §3.3.

Page-category breakdown within `page_views` reuses the existing PUBLIC `subject.page_type` field from `visitor.page_viewed` (`home|singular|search|archive|other`) — no new field, no new classification.

### 3.1 Interaction with M02 rules

`RuleEvaluator::evaluate()` (`src/Automations/RuleEvaluator.php:53`) is the single point every notification rule passes through, called by `Events\EventDispatcher::handle()` immediately after history-projection. M11A adds one narrow, structural guard at the top of `evaluate()`: if `$event->event_type()` is in a fixed constant `DigestEligibility::SUPPRESSED_EVENT_TYPES` (the six types in §3 plus `visitor.session_started` — seven total) **and** `DigestEligibility::is_active()` currently returns `true`, the method returns immediately, after recording one `DispatchLogRepository::record_rejected()` call per matching enabled rule with a new `DispatchLogResult::SKIPPED_SUPPRESSED_BY_DIGEST` code (new enum case, `src/Automations/DispatchLogResult.php`), **before** any digest aggregation runs. If `is_active()` returns `false`, the guard does nothing at all and `evaluate()` proceeds exactly as it does today — the event's matching rules dispatch individually, unchanged, exactly as if M11A did not exist.

**`DigestEligibility::is_active()` is the single shared gate for both suppression and aggregation** (§5), defined as: `visitor_digest_enabled === true` AND the saved `visitor_digest_bot_id` resolves to a `BotProfile` with `BotStatus::ACTIVE` AND the saved `visitor_digest_destination_id` passes the full destination-eligibility rule in §4 (enabled, belongs to that bot, not conversation-linked). This directly implements the corrected requirement: **suppression is opt-in, active only once digest delivery is enabled and its target is genuinely valid.** A freshly installed or default-configured site (`visitor_digest_enabled = false`) suppresses nothing — every existing visitor-event rule keeps working exactly as it did before M11A, and batching remains something an administrator must deliberately turn on, never a silent behavior change.

**Cost control and invalidation:** `is_active()` cannot afford a live bot/destination database lookup on every single visitor event (§8's "must not block" constraint), so its result is cached in a WordPress transient, `universal_telegram_visitor_digest_active` (`'1'`/`'0'`). This cache is invalidated **immediately and unconditionally** — never left to expire — on every write that could change the answer: (a) the digest settings-save handler (§4) deletes it on every save of the five digest fields; (b) a new `universal_telegram_bot_or_destination_changed` action, fired **from inside the repository/service mutation methods themselves, after each successful write** — `BotProfileRepository::set_status()`, `mark_registered()`, `mark_unregistered()`, `mark_uncertain()`, `delete()`, and `DestinationRepository::create()`, `set_enabled()`, `delete()`, `delete_for_bot()` each fire it once their own `$wpdb` write succeeds (never on a failed write) — on which `DigestEligibility` registers a deletion callback. Firing from the repository layer itself, rather than from any one caller such as the Bots admin screen, means **every** path that mutates a bot or destination is covered by construction, regardless of which higher-level code initiates it: the manual Bots tab, the bot setup wizard, the webhook-registration flow (which calls `mark_registered()`/`mark_unregistered()`/`mark_uncertain()`), a retention/cleanup routine, or any future administration screen not yet written — none of them needs to know the digest feature exists, since the hook lives at the one layer every one of them already passes through. This keeps the dependency one-directional (the `Telegram` boundary fires a generic domain event from its own repositories; the `Automations` boundary, which already depends on `Telegram` per ADR-0012, listens, never the reverse). The transient's **30-second TTL is retained only as a bounded fallback**, not as the primary invalidation mechanism, for the one case the hook cannot observe: an out-of-band database change (direct SQL, a multisite network-wide update, a restored backup, or a replica-lag read) that alters bot/destination state without going through either repository's own PHP write path at all. This plan states honestly that such an out-of-band change can leave suppression active, and a genuinely invalid target undetected, for **up to 30 seconds** before the next natural recomputation (the transient's own expiry, or the sweep's unconditional per-tick refresh, §5) restores direct-rule delivery — a small, explicitly bounded and disclosed window, not an indefinite one.

**Recovery behavior:** if `visitor_digest_enabled = true` but the target is currently invalid, `is_active()` returns `false`: suppression is lifted and every matching visitor-event rule resumes firing individually immediately — there is no notification blackout while a misconfiguration exists. Any digest window already open at the moment the target became invalid is left exactly as-is (counters frozen, not deleted, not force-sent) — see §5. As soon as the administrator repairs the target (re-enables the bot, re-enables/recreates the destination), `is_active()` returns `true` again on its next check and normal digest behavior — suppression and aggregation together — resumes automatically, with no manual "resume" step and no special-cased resume code path, since the frozen window's counters were never touched while inactive.

Any existing enabled `notification_rules` row whose `event_type` is one of the seven digest-eligible types keeps its row, its `enabled` flag, and its configuration completely untouched regardless of digest state (no destructive migration, ever) — it simply dispatches individually whenever `is_active()` is `false` (including the default, digest-disabled state) and is suppressed only while `is_active()` is `true`. The Automations rule-list admin screen gains a **live, state-reflecting** badge — "Currently batched by Visitor Digest" when `is_active()` is `true` for that rule's event type, versus no badge at all when it is `false` — computed from the same shared gate, not a static "always superseded" label, so the UI never implies a permanence the underlying behavior doesn't have. `RuleSimulator` surfaces the same live state when previewing a rule against one of the seven types.

New rule creation against one of the seven event types is not blocked at the data layer or hidden from the rule-builder UI — since suppression is conditional, not permanent, a rule an administrator configures today may legitimately fire individually tomorrow if the digest is later disabled, so hiding the event type from the picker would remove a real, valid choice. Instead the rule-builder shows a one-line, live-state note ("This event type is currently batched by Visitor Digest and will not send individually while that remains enabled and configured") only when `is_active()` is `true` for that type.

### 3.2 Migration/compatibility

No data migration marks or disables existing rules (see above — inert-by-evaluator, not deleted or flagged in storage). `db_version` gains two additive migration steps, 23 and 24 (see §5), for the new digest tables only; no existing table's schema changes.

### 3.3 JavaScript-error decision (resolved)

**Decision: retain the existing per-rule immediate-alert path unchanged; JavaScript errors are excluded from digest suppression and from digest content.** `visitor.javascript_error` is not added to `DigestEligibility::SUPPRESSED_EVENT_TYPES`. Any administrator-configured `notification_rules` row for `visitor.javascript_error` continues to fire exactly as it does today, through the unmodified M02 path, protected by the same `cooldown_seconds` field every rule already has (no new rate-limit mechanism is built) plus M04's own existing client-side 5-per-tab-session cap. Rationale: decision 5 itself frames JS errors as "exceptional," and this milestone's charter (M11) separately lists "error clustering" as its own deferred, unscheduled deliverable — building a bespoke digest/count-only path for errors now would duplicate work a later, dedicated error-digest milestone slice should own, and would remove existing operator visibility into errors before that replacement exists. This is a one-line "no changes needed" confirmation folded into WP2 (§9), not new code.

## 4. Delivery-target settings

New settings fields, added to `Core\Configuration\Settings::defaults()`/`sanitize()` following the exact existing pattern (e.g. `visitor_sampling_percent` at `Settings.php:67`,`:143`) — **no new settings system**:

| Field | Type | Default | Validation |
|---|---|---|---|
| `visitor_digest_enabled` | bool | `false` | cast bool |
| `visitor_digest_bot_id` | int\|null | `null` | must reference an existing `BotProfile` with `BotStatus::ACTIVE` at read time (re-validated live, not at save time only — bot status can change after save) |
| `visitor_digest_destination_id` | int\|null | `null` | must satisfy the full eligibility rule below at read time, not save time only |
| `visitor_digest_threshold` | int | `50` | clamp `10–500` |
| `visitor_digest_max_wait_minutes` | int | `15` | clamp `5–60` |

**Digest-target destination eligibility (exact rule).** A destination is a valid digest target if, and only if, all of the following hold, re-checked live on every read (never cached beyond the transient in §3.1):

1. It belongs to `visitor_digest_bot_id` and is `enabled()` (`DestinationRepository::for_bot()`/`find()`, same as any other destination reference in this codebase).
2. It is a **stable, administrator-configured** destination — one an administrator created directly through the Bots tab, not one the plugin created automatically. Concretely: its `id` must **not** appear in `ConversationRepository::destination_ids_for_bot( $bot_id )` — the exact, already-existing method `Administration\Telegram\BotManagementPage.php:316` uses today to identify and exclude conversation-created topic destinations from the manual destination list (ADR-0024's own "destination-list hygiene" mechanism). This is the precise, join-based exclusion, not a heuristic on `message_thread_id` alone — a manually-configured forum-topic destination (non-null `message_thread_id`, not tied to any conversation) remains eligible; only a destination genuinely created by, and currently linked to, a chat-widget conversation is excluded. As a defense-in-depth backstop against an orphaned/stale link, a destination is also excluded if its `message_thread_id` is non-null **and** its `id` matches any `conversations.destination_id` value regardless of that conversation's current status — the same query, expressed without the bot-scoped helper, for the rare case a conversation row outlives its own destination's normal lifecycle.

The settings-page dropdown (§4 UI, below) populates only destinations passing this rule — a conversation-linked destination never appears as a selectable option in the first place. If a **previously saved** `visitor_digest_destination_id` fails this rule on a later read (the conversation it was quietly reassigned to no longer exists, or an administrator deletes/disables it, or it becomes conversation-linked through some future code path), `DigestEligibility::is_active()` (§3.1) returns `false` exactly as it does for any other invalid-target case: suppression lifts, direct-rule delivery resumes under the existing safety fallback, and Diagnostics (§7) reports `visitor_digest_paused_invalid_target` — no special-cased handling beyond reusing the same fallback this plan already defines for a disabled bot or destination.

Delivery is a **bot + destination pair**, never an implicit default (frozen decision 2): the settings UI (new fieldset on the existing Visitor Tracking admin page, `Administration\Visitor\VisitorTrackingPage.php` — same screen as the rest of M04's visitor settings, not a new top-level page) presents a bot dropdown (`BotProfileRepository::all()`, filtered to `BotStatus::ACTIVE`) and, once one is chosen, a destination dropdown scoped to that bot and filtered by the full eligibility rule above (`DestinationRepository::for_bot()`, filtered to `enabled()` **and** excluded from `ConversationRepository::destination_ids_for_bot()`) — a conversation-linked destination is never offered as a choice, so an administrator cannot select an ineligible target through the UI in the first place; only a saved reference that becomes ineligible *after* being selected (via the backstop case above, or any later bot/destination mutation from any caller — §3.1) can produce the invalid-target state below. This mirrors the two-step selection pattern already implied by ADR-0012's bot/destination model. If a saved reference becomes ineligible later — bot deactivated, destination disabled/deleted, or (backstop) newly conversation-linked — `DigestEligibility::is_active()` (§3.1) flips to `false`: suppression is lifted, direct rule delivery for the affected event types resumes automatically under the existing safety fallback, and the sweep (§5) leaves any already-open window frozen rather than sending or discarding it, logging `visitor_digest.send_skipped_invalid_target` and surfacing the condition in Diagnostics (§7) — never a silent, unexplained stop. Reuses the existing `CapabilityRegistrar::MANAGE` capability and the existing settings-page nonce/capability check pattern already used by every other Visitor Tracking field — no new capability constant, consistent with M04's own precedent and rationale (§6 of the M04 plan).

## 5. Digest aggregation and persistence design

**New table** `universal_telegram_visitor_digest_counters` (one open aggregation window at a time — a single-row-per-category "bucket," not one row per event):

```
id                 BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
window_started_at  DATETIME NOT NULL      -- set once, at first eligible event after the prior window closed
category           VARCHAR(32) NOT NULL   -- page_views | product_views | search | cart_intent | other
page_type          VARCHAR(16) NULL       -- home|singular|search|archive|other; only for page_views rows
event_count        BIGINT UNSIGNED NOT NULL DEFAULT 0
last_event_at      DATETIME NOT NULL
UNIQUE KEY window_category_page (window_started_at, category, page_type)
```

`visitor.session_started` increments a `category = 'other'`, `page_type = NULL` row (counted for suppression/completeness, never itself broken out in the rendered digest — folded into a documented "other" line only if non-zero, §6).

**Second table**, `universal_telegram_visitor_digest_state` — a single seeded row (`id = 1`), the same "singleton row as mutex/checkpoint" pattern ADR-0028 already established for `universal_telegram_ai_config`:

```
id                    TINYINT UNSIGNED PRIMARY KEY (=1)
window_started_at     DATETIME NULL   -- NULL when no window is currently open
last_digest_sent_at   DATETIME NULL
last_digest_status    VARCHAR(32) NULL  -- sent | send_failed | skipped_invalid_target | skipped_no_events
claim_token           VARCHAR(36) NULL
claim_expires_at      DATETIME NULL
```

**Cursor/checkpoint model:** aggregation does not read `event_history` retroactively — it increments counters synchronously, in the same `EventDispatcher::handle()` call that already writes the history row (§3.1), gated by the exact same `DigestEligibility::is_active()` check the suppression guard uses (one shared gate, §3.1): a counter increment happens if, and only if, a suppression would also happen for that event. This is deliberate — it means a window can only ever accumulate events during a period when direct delivery for those events was actually suppressed, so the digest a window eventually produces always reconciles with "what was not sent individually," never with events that were also delivered individually (no double-reporting). While `is_active()` is `false` (digest disabled, or enabled with an invalid target), no counter row is touched at all; if a window was already open when the gate flipped to `false`, it is simply left alone — frozen, not deleted, not force-sent — and resumes accumulating (or becomes eligible to send, §5 below) automatically once the gate returns to `true`, with no special resume logic required, since nothing about the frozen row changes while inactive. `window_started_at` is set by the aggregator on the first eligible event after `visitor_digest_state.window_started_at` is `NULL`, using a single `INSERT ... ON DUPLICATE KEY UPDATE window_started_at = window_started_at` idiom guarded by first checking-and-claiming the state row, so concurrent requests opening a window race safely to the same timestamp.

**Threshold/max-wait scheduling:** a new Action Scheduler recurring action, `visitor_digest_evaluation_sweep`, registered via `as_schedule_recurring_action()` exactly like every other recurring job in `Core\Plugin::init()` (`src/Core/Plugin.php:824` pattern), interval **60 seconds** (fine-grained enough that a 5-minute-minimum max-wait is honored within one minute of expiry, matching this codebase's existing sweep-cadence precedent from `AiDraftLeaseSweep`'s 60-second cadence). Each tick: (1) lock `visitor_digest_state` (`SELECT ... FOR UPDATE`) as the sole admission mutex — identical pattern to ADR-0028 decision 5's config-row lock; (2) recompute and refresh the `DigestEligibility::is_active()` cache transient (§3.1) unconditionally, so a target-validity regression is caught even during a quiet period with no visitor traffic to trigger the recheck; (3) if no window is currently open, release and exit; if a window is open but `is_active()` is now `false` (digest disabled, or enabled with an invalid target), release and exit without evaluating threshold or sending — the window is left exactly as-is, neither sent nor discarded, and is re-checked again next tick, resuming normal evaluation automatically once `is_active()` returns `true`; (4) otherwise, sum `event_count` across all rows for the current `window_started_at`; (5) eligible to send if `sum >= visitor_digest_threshold` **or** `now - window_started_at >= visitor_digest_max_wait_minutes` (either-condition-met, per frozen decision 3); (6) if eligible, claim (`claim_token`/`claim_expires_at`, 120-second lease — long enough for a Telegram round-trip via M01's existing queue handoff), render and hand off exactly one `OutboundMessage` through `Telegram\Outbound\MessageDispatcher::send()` unchanged (§8, reusing ADR-0012's pattern the same way `NotificationDispatcher::dispatch()` already does at `src/Automations/NotificationDispatcher.php:89`); (7) on `DispatchState::SCHEDULED`, atomically close the window (`window_started_at = NULL`, `last_digest_sent_at = now()`, `last_digest_status = 'sent'`) and delete/archive that window's counter rows in the same transaction; on failure to hand off, leave the window open (no data loss — next sweep tick retries) and record `send_failed`, capped by M01's own existing outbound retry/circuit-breaker (ADR-0014), never a new retry mechanism.

**Duplicate/crash safety:** the counter increment and the window-close-plus-send-handoff are the only two writes that matter for correctness. Because `MessageDispatcher::send()` durably persists the `OutboundMessage` row *before* returning `SCHEDULED` (ADR-0012's own design — content written to a durable, encrypted table before any queue job exists), a crash between handoff and window-close can, at worst, leave a window open with counters that a subsequent sweep re-evaluates and re-sends. This plan accepts an **honest at-least-once** digest-send guarantee (a rare duplicate digest message is a bounded, low-severity cost, not a correctness violation — the same posture ADR-0028 already accepted for AI draft generation), never claiming exactly-once. The 120-second claim lease plus the state-row mutex prevents two concurrent sweep ticks (e.g. overlapping cron and manual trigger) from double-sending the same window.

**Retention:** counter and state rows are aggregate-only and contain no visitor-identifying data; they are retained until their window closes (typically minutes) and are not subject to `event_retention_days` (they are not `event_history` rows). No new retention setting is introduced. Uninstall drops both new tables unconditionally, following the existing uninstall convention for all other plugin-owned tables.

**`db_version`:** two additive migration steps, 23 (create `visitor_digest_counters`) and 24 (create `visitor_digest_state`, seeding the one `id=1` row as part of the migration itself — same precedent as ADR-0028 step 19). `db_version` 22 → 24. No existing table is altered.

## 6. Digest message format

Fixed structure, MarkdownV2-safe (escapes timestamps and other dynamic punctuation via the shared
`Automations\MarkdownV2Escaper`, also used by `TemplateRenderer` and the operational summary
renderer — raw DATETIME/`(N min)` text must not be sent unescaped under `parse_mode=MarkdownV2`):

```
📊 *Visitor Activity Digest*
Window: {window_started_at} – {sent_at} ({duration} min)

Page views: {page_views_count}
  • Home: {n}   • Product/post: {n}   • Search: {n}   • Archive: {n}   • Other: {n}
Product views: {product_views_count}
Searches performed: {search_count}
Cart/checkout intent: {cart_intent_count}
{other_count, only if > 0:}Other activity: {other_count}

Total events: {grand_total}
```

Category lines with a zero count are omitted entirely except the always-present four top-level lines (`page_views`/`product_views`/`search`/`cart_intent` render as `0` rather than being hidden, so an administrator can distinguish "no activity of this kind" from "this category doesn't exist"); the page-type sub-breakdown line is omitted if `page_views_count = 0`; product-view/cart-intent lines are omitted entirely (not shown as `0`) when WooCommerce is inactive, since those categories cannot occur. **Empty-window behavior:** the sweep never sends a digest for a window with `grand_total = 0` — a window only opens on a real eligible event (§5), so a zero-total send is structurally impossible, not a case requiring special-cased suppression logic. Message length is bounded by construction (fixed line count, each count is a bounded integer) and is always far under Telegram's 4096-character limit — no truncation logic is needed or added.

## 7. Privacy/security/audit/diagnostics matrix

| Field | Classification | Notes |
|---|---|---|
| category, page_type, all counts | PUBLIC (reuses existing PUBLIC classification already established for these fields in `Registry`, M04 plan §4.2) | No new classification map entries — counters are integers and enum values, not event fields, so they are not routed through `Privacy\Redactor` at all; the underlying source events were already redacted-and-classified before ever reaching the aggregator |

No URL, path, query string, referrer, visitor/session identifier, name, email, user ID, free text, search term, error text/stack, location, raw payload, credential, or internal database ID is ever placed in a rendered digest message or in the counter table — enforced structurally: the counter schema (§5) has no column capable of holding any of those, mirroring the same "structural, not policy" guarantee ADR-0019 already established for the ingestion endpoint. A new PHPUnit guard test (`VisitorDigestPrivacyTest`) asserts the rendered message template contains none of a fixed denylist of field names, following the same pattern as M04's WP7 "full-catalog PII-denylist audit test."

Configuration audit: saving digest settings goes through the existing settings-save audit entry (already logs field-diff with the plugin's existing classification map, ADR-0009) — `visitor_digest_bot_id`/`visitor_digest_destination_id` are INTERNAL, never SECRET, so no redaction change is needed.

**Diagnostics additions** (`Administration\Diagnostics\DiagnosticsReport::generate()`, additive keys, same pattern as M04's WP6):
- `visitor_digest_enabled`
- `visitor_digest_target_valid` (bool — live-checked bot/destination validity)
- `visitor_digest_active` (bool — `DigestEligibility::is_active()`'s own value: `enabled && target_valid`; this, not `enabled` alone, is what actually governs suppression, §3.1)
- `visitor_digest_paused_invalid_target` (bool — `enabled = true` but `target_valid = false`; the specific misconfiguration case where direct-rule delivery has been automatically restored as a safety fallback, surfaced as an explicit warning distinct from "intentionally disabled") — this is the primary diagnostic the corrected suppression design (§3.1) exists to make visible, since the design's whole point is that this state is never a silent blackout, only a visible, self-healing pause
- `visitor_digest_pending_event_count` (current open window's `grand_total`)
- `visitor_digest_oldest_pending_age_seconds` (now − `window_started_at`, null if no window open)
- `visitor_digest_last_sent_at`
- `visitor_digest_last_status` (`sent|send_failed|skipped_invalid_target|skipped_no_events|never_run`)
- `visitor_digest_currently_suppressed_rules_count` (count of enabled `notification_rules` rows whose `event_type` is in `SUPPRESSED_EVENT_TYPES`, computed **only while `visitor_digest_active` is true** — `0` whenever the digest is disabled or paused, since no rule is actually suppressed at those times; a live count, not a static "these rules are affected" list, matching the rule-list badge's own live-state semantics)

## 8. Reliability and performance

Counter increments happen inside the same synchronous `EventDispatcher::handle()` request path visitor events already traverse — this is one additional `INSERT ... ON DUPLICATE KEY UPDATE event_count = event_count + 1` per eligible event, on a small, narrowly-indexed table, no heavier than the existing `event_history` write it sits beside; it introduces no new external call and cannot block page rendering, checkout, or WooCommerce activity (frozen decision 9) since it never leaves the same PHP request that was already writing to the database for the pre-existing history/rule-evaluation path. The sweep itself runs entirely on Action Scheduler's own background worker, identical isolation to every other recurring job in this codebase (RetentionCleanup, AiDraftLeaseSweep, etc.) — never inline with a frontend request. Telegram failure during send-handoff is absorbed entirely by M01's existing retry/circuit-breaker/dead-letter machinery (ADR-0014) once `MessageDispatcher::send()` has been called; a circuit-open state simply means `send()` returns a non-`SCHEDULED` state, the window stays open, and the next sweep tick tries again — no new failure-handling code path. Destination/target changes take effect on the very next sweep tick (settings are read live, not cached — same pattern as M04's `IngestController` re-validating every setting live). Schema upgrade (`db_version` 23→24) is two additive `CREATE TABLE` steps with no data migration and no lock risk to any existing table. `event_history` retention cleanup (M02's `RetentionCleanup`) is entirely independent of digest counters, which are never sourced from `event_history` reads (§5) — a retention sweep deleting old history rows cannot affect an in-flight or already-aggregated digest window. WooCommerce-absent behavior: `product_views`/`cart_intent` categories simply never receive events (their source event types are WC-gated at registration, unchanged from M04) — the digest renders those categories as fully omitted, not as a zero-value line (§6), so an administrator without WooCommerce sees a leaner, honest message.

## 10. ADR-0029 (proposed, full text)

# ADR-0029 — M11A: Non-AI Visitor Activity Digest as a First Slice of M11

## Status
Proposed

## Context
M11's charter (`docs/milestones/m11-digests-and-operational-intelligence.md`) is a single undivided milestone spanning scheduled summaries, threshold alerts, checkout-failure detection, funnel summaries, error clustering, AI-assisted internal summaries, and destination-specific reporting, deliberately kept whole because its AI-summary deliverable depends on M09. M09 is implemented (ADR-0028) but its Product Owner acceptance is still pending. Meanwhile, M04's visitor/browser event coverage (ADR-0019) already produces enough routine event volume that an administrator with any notification rule configured against a high-frequency `visitor.*` event type receives one Telegram message per page view — a live, present-day noise problem entirely independent of AI and not requiring M09 to fix. Waiting for full M11 (and, transitively, M09's acceptance) to address it is disproportionate to the narrow, non-AI fix available today.

## Decision
M11 is executed in two slices. **M11A** — this ADR — covers exactly: scheduled site-wide aggregate visitor-activity digests, administrator-configurable threshold/max-wait batching, a bot+destination delivery target, and suppression of direct per-event Telegram delivery for a fixed set of low-severity `visitor.*` event types. M11A depends only on M02 and M04 (both closed), not on M09, and does not require M09's Product Owner acceptance to begin or close. The remainder of M11 — threshold alerts beyond the visitor-digest case, checkout-failure detection, funnel summaries, error clustering, AI-assisted internal summaries, and destination-specific reporting beyond the one visitor-digest target — remains a single future slice, still dependent on M09 exactly as the original charter states, and is not reduced in scope, reordered, or implied complete by M11A's closure. M11's own charter document is updated (docs-only, no code) to record this split and to state explicitly that M11A's closure does not close M11.

## Alternatives
- *Wait for M09 acceptance and execute all of M11 as one slice, as originally chartered.* Rejected: the visitor-noise problem is present today, has no technical dependency on M09 or AI, and delaying it couples an unrelated administrative-UX fix to an unrelated pending Product-Owner decision.
- *Fix visitor-event noise inside M04 itself, retroactively, without a new milestone or ADR.* Rejected: M04 is closed; reopening a closed milestone's charter to add scheduled-digest behavior it never scoped would violate `docs/governance.md`'s "changing a frozen milestone charter" process more severely than a forward-looking, explicitly-scoped M11 sub-slice does.
- *Renumber this work as a new milestone (e.g. M11.5) rather than a lettered slice of M11.* Rejected: the work is squarely inside M11's own already-chartered "scheduled summaries" and "threshold alerts" deliverables — it is a slice of M11's existing scope, not a new product concern requiring its own milestone number.

## Consequences
M11's charter and closure record (once M11 as a whole eventually closes) must reference both this ADR and M11A's own closure record, so the milestone's full lineage — split, first-slice closure, and eventual full-M11 closure — is traceable. Any later architecture decision touching M11's remaining (AI-dependent) portion must treat M11A's suppression mechanism (`DigestEligibility::SUPPRESSED_EVENT_TYPES`, `RuleEvaluator` guard) as an existing, reusable pattern for any further event type that later portion decides to route through a digest rather than a direct rule.

## Security and privacy impact
None beyond what M11A's own implementation plan documents in full (privacy-minimal aggregate-only digest content, no new visitor-identifying data). This ADR itself is a scope/boundary decision, not a technical control.

## Affected Documents/Milestones
`docs/milestones/m11-digests-and-operational-intelligence.md` (status/scope note, no charter rewrite); `docs/governance.md` (cited, not amended — this ADR is itself the required scope-change record); M11A's own implementation plan and closure record; the remainder of M11, unaffected in scope, still gated on M09 acceptance.

## Compatibility/Migration Impact
None directly — this ADR authorizes a milestone-execution split; M11A's own plan (§5 above) carries the actual schema impact (`db_version` 22→24).

## Self-review checklist (completed)

- **Bot vs destination:** §4 requires both, live-revalidated, never an implicit default — matches frozen decision 2.
- **Threshold/timeout semantics:** §5 sweep step 4 is explicitly either-condition-met, both administrator-configurable within the frozen ranges — matches frozen decision 3.
- **No per-visitor identity/sensitive detail:** §5 schema and §7 matrix contain only categories/counts/enums, structurally incapable of anything else — matches frozen decisions 1 and 6.
- **No accidental direct-notification spam path:** §3.1's evaluator-level suppression fires only for the seven digest-eligible types AND matches frozen decision 4's intent while additionally correcting the risk the Product Owner flagged: suppression is conditional on `DigestEligibility::is_active()`, so a disabled or misconfigured digest never suppresses anything — direct-rule delivery is the default, and batching must be deliberately turned on, matching the Product Owner's explicit correction that "administrators silently lose notifications" is unacceptable.
- **No notification blackout from misconfiguration:** §3.1/§5 — if `visitor_digest_enabled` is true but the bot/destination target becomes invalid, `is_active()` flips to false via the change-triggered `universal_telegram_bot_or_destination_changed` action (immediate) or, for an out-of-band DB change, within the disclosed 30-second TTL fallback; suppression lifts, and Diagnostics (§7) surfaces `visitor_digest_paused_invalid_target` so the condition is visible, not silent.
- **Digest target cannot be a conversation topic:** §4's destination-eligibility rule excludes any destination in `ConversationRepository::destination_ids_for_bot()` (reusing ADR-0024's own destination-list-hygiene method) plus a backstop `message_thread_id`+`conversations.destination_id` check, from both the settings dropdown and every live re-validation — a chat-widget conversation topic can never become, or silently remain, the digest target.
- **Baseline and click-removal corrections applied:** §1 rebased to `main == origin/main == 7011163` / `0.11.1` / `db_version 22`; `visitor.click` removed from the catalogue (§3), the suppressed-type set (§3.1, now cleanly "six types + session_started = seven"), and every test/work-package reference — no residual mention of it as an active or planned source.
- **Invalidation hook lives at the repository layer, not one admin screen:** §3.1/§9 WP1 — `universal_telegram_bot_or_destination_changed` fires from inside `BotProfileRepository`'s and `DestinationRepository`'s own mutation methods after each successful write, so the setup wizard, webhook registration, cleanup routines, and any future administration screen are covered by construction, not just the Bots tab; WP1's new regression test drives the repositories directly (bypassing `BotManagementPage` entirely) to prove this. §3.2's migration-step count corrected to "two additive steps, 23 and 24," matching §5/§9 throughout.
- **Durability/duplicate/loss behavior:** §5 — counters written synchronously in the same request as history; at-least-once send with honest documentation, no data loss on crash (window stays open) — matches frozen decision 7.
- **Event-history retention interaction:** §8 — digest counters never read from `event_history`, so retention cleanup cannot affect an open or in-flight window.
- **Work-package/test traceability:** §9 — every WP names files, DB impact, and tests.
- **ADR/documentation paths and numbering:** ADR-0029 is the next free number after ADR-0028; `docs/milestones/m11-*.md` gets a status note only, no destructive rewrite.
