## 0. Prerequisite (WP0, blocking): M05 idempotency extension

The widget must be able to retry `POST /conversations` and `POST /messages` after a network/`5xx` failure without risking a duplicate conversation or duplicate message. **This cannot be solved in JavaScript alone** — it requires a small server-side extension to M05's persistence and REST contract, sequenced as **WP0, before WP4 (REST client)**. Message-level retry is covered in §3; **start** uses the following single, fully resolved protocol (no alternatives):

**Start idempotency protocol (`POST /conversations`):**

1. Before dispatch, the browser generates **both**: a random `Idempotency-Key` (opaque, e.g. UUIDv4), and the 256-bit conversation bearer secret itself (client-generated, not server-generated — 32 random bytes, hex-encoded to 64 lowercase hex characters, the same format `VisitorTokenGenerator` already produces server-side today, so no format change ripples elsewhere).
2. The browser writes the pending-start state to `sessionStorage` **before** dispatch (exact shape in §2), then sends `POST /conversations` with an **empty JSON body** (`{}`) and two headers: `Idempotency-Key: <key>` and `X-Universal-Telegram-Conversation-Secret: <secret>`. Neither value ever appears in a URL, query string, request body, response body's request-echo, log line, diagnostic output, or any server-rendered/cached HTML — both are headers only, read once by the handler.
3. M05 validates the secret's format (64 lowercase hex characters; anything else is rejected the same way as any other malformed start request — generic `400`, `{ok:false}`, no distinguishing detail). If the `Idempotency-Key` has not been seen before, M05 creates a new conversation row storing **only** `password_hash(secret)` (via `password_hash()`, exactly as `VisitorTokenGenerator::generate()` already does) and the unique `start_idempotency_key` value (new column, unique index) — the plaintext/raw secret is never written anywhere, encrypted or not.
4. If the `Idempotency-Key` **has** been seen before (a replay), M05 looks up the conversation by that key and verifies the request's `X-Universal-Telegram-Conversation-Secret` against the stored hash via `password_verify()`. On a match, it returns the same `200` shape as a fresh start — `{ok:true, conversation_uuid, secret}` — where `secret` is simply the **caller-supplied** value echoed back (the server never needed to store or re-derive it; it only ever needed to verify it). No new row is created.
5. If the `Idempotency-Key` is known but the supplied secret is missing or fails `password_verify()`, M05 returns the **same controlled failure shape** used for any other start rejection (generic `400`, `{ok:false}`) — identical in structure to the malformed-request case in step 3, so an attacker probing idempotency keys learns nothing about whether a given key exists or what its correct secret is.
6. **Retention:** the `start_idempotency_key` column is retained only as long as the conversation row it's attached to — cleaned up by the same existing retention job ADR-0021 already defines (`RetentionCleanupHandler` deletes the row; the column goes with it). No separate idempotency store.

**Database migration (mandatory part of this WP, not optional):** both new columns are added to the two existing M05 tables via one new numbered `Migrator` step, `step_13_add_conversation_idempotency_columns()` (`src/Persistence/Migrator.php`, following the exact pattern of `step_11`/`step_12`: raw `ALTER TABLE` via `$wpdb->query()`, no `dbDelta()`), bumping `target_version()` from `12` to `13`. **No new table.**

- `universal_telegram_conversations`: `ADD COLUMN start_idempotency_key CHAR(36) NULL`, `ADD UNIQUE KEY start_idempotency_key (start_idempotency_key)`. Nullable and unique: pre-migration rows get `NULL`, and MySQL/MariaDB unique indexes permit any number of `NULL`s without collision, so existing conversations are unaffected and the migration is upgrade-safe with no backfill needed.
- `universal_telegram_conversation_messages`: `ADD COLUMN idempotency_key CHAR(36) NULL`, `ADD UNIQUE KEY conversation_idempotency (conversation_id, idempotency_key)`. Same nullability/uniqueness reasoning — a composite unique key scoped to the conversation, `NULL` for all pre-migration rows.
- `verify_step_13()` follows the existing `table_has_columns()` postcondition pattern, checking both new columns exist on both tables before the schema-version option advances (same "never partially advances" guarantee documented on `Migrator`).
- Retention cleanup requires no new code: both columns live on rows already deleted by the existing per-table retention job, so they are purged automatically with the row.

**Message idempotency (`POST /conversations/{uuid}/messages`):** unchanged in shape from before — a per-message `Idempotency-Key` header, unique per `(conversation_id, idempotency_key)`; a replay returns the original message's success response without inserting a duplicate row. Unlike start, this key is **not** persisted to `sessionStorage` (see §2 for why: it's generated and held in memory only for the lifetime of one pending send, since there is no reload-survival requirement for an unacknowledged single message — see §2/§3).

**ADR:** this amends **ADR-0021** (it directly extends the persistence/auth contract that ADR already defines) rather than requiring a new ADR; ADR-0005 needs no change (no new boundary, no composition change). Full amendment text is in §10.

This is recorded as **WP0, an M05 corrective/prerequisite package** in this M06 plan (§8) — it is planned, not implemented, in this pass.

## 1. Architecture

**New files** (all under a new `ChatWidget` boundary per ADR-0005/ARCHITECTURE.md row 10):

- `src/ChatWidget/ChatWidgetAvailability.php` — pure service: `is_available(): bool` = existing Settings option `chat_widget_enabled` (bool, default false) AND `ChatProfileResolver::default_bot()` returns a bot with an eligible destination (reuses `ChatProfileResolver::conversation_chat_id()` logic — no duplicated eligibility rule).
- `src/ChatWidget/ChatWidgetAssets.php` — mirrors `src/Events/Visitor/TrackerAssets.php`: hooked on `wp_enqueue_scripts`; `should_enqueue()` reuses the same nine-condition cache-safety gate (admin/ajax/cron/REST/feed/robots/trackback/JSON/login excluded) plus `ChatWidgetAvailability::is_available()`; enqueues `assets/js/chat-widget.js` and `assets/css/chat-widget.css` via `plugins_url()` + `UNIVERSAL_TELEGRAM_VERSION` cache-buster; injects config as a static JSON data island (§4), never `wp_add_inline_script`.
- `assets/js/chat-widget.js` — single vanilla file, no bundler/framework (matches the existing `visitor-tracker.js` convention and the "no React/Vue" boundary), split internally into three responsibilities for testability: `state` (sessionStorage), `client` (fetch/poll), `ui` (DOM/a11y).
- `assets/css/chat-widget.css` — static stylesheet, CSS custom properties for color/spacing only (no live-preview, no scoped editor — deferred per scope decision above).

**Settings wiring:** extend the existing `SettingsPage` (`src/Administration/Hub/SettingsPage.php`, `TAB_ID = 'settings'`) rather than adding a new Hub tab — the charter does not require a dedicated widget administration screen, and a single toggle doesn't warrant one. Add:
- A new `BOOLEAN_FIELDS` constant (parallel to existing `INTEGER_FIELDS`) containing `chat_widget_enabled`, with a `BOOLEAN_FIELD_LABELS` entry `'chat_widget_enabled' => 'Enable chat widget'`.
- One checkbox row in the existing render method, using the existing `ADMIN_POST_ACTION`/`NONCE_ACTION` save flow (`SettingsPage.php:34-35`). Save logic must treat an absent checkbox POST field as `false` (standard HTML checkbox semantics), not skip the field.
- No new capability — reuses `CapabilityRegistrar::MANAGE`, same as the tab's existing registration at `Plugin.php:932`.

**Disabled/unavailable/JS-failure behavior:**
- Setting off, or no eligible bot/destination → `ChatWidgetAssets::should_enqueue()` returns false → nothing is enqueued, nothing rendered, zero footprint (no dead markup, no config island).
- M05 REST unavailable at runtime (e.g. `handle_start` returns 503 because `default_bot()` became null after page load, a TOCTOU race) → widget was enqueued (looked available at render time) but the first send fails → client maps this to the **unavailable** state (§5), not transient-failure, since a 503 on start specifically means "no bot configured," matching the exact code path at `ConversationsController.php` (start handler, `null === $bot` branch).
- JS disabled/fails to load → only static CSS/markup absent; nothing else on the page is affected (assets are a single independent enqueue, no shared script dependency with cart/checkout/tracking assets).

## 2. Visitor state & token storage

- **Mechanism:** `sessionStorage` only. No cookies, no `localStorage`, no cross-site identity.
- **Keys:** two, used at different lifecycle points, both under the same storage mechanism:
  - **`utChatPendingStart`** — written **before** the `POST /conversations` dispatch, holding exactly `{ idempotencyKey, secret }`. This is what lets a reload that happens while start is in flight retry the *same* request (§3) instead of orphaning a conversation. Cleared the moment a `200` (fresh or replayed) is received and replaced by `utChatConversation`; also cleared on a terminal start failure (§3), since a terminal failure means no conversation exists to resume toward.
  - **`utChatConversation`** — written on start success, holding `{ uuid, secret, startedAt }`. No message text and no message cursor are persisted here (see Reload below).
  - A **per-message** idempotency key exists only in memory (a property on the in-flight/pending message object in `chat-widget.js`), never in `sessionStorage`: an unacknowledged single message does not need to survive a reload — if the send actually succeeded server-side before the reload, the hydration poll (§3) will show it in the transcript; if it didn't, the visitor simply resends. Persisting an open-ended set of per-message keys for a scenario the hydration poll already handles correctly would add storage/cleanup complexity with no behavioral benefit, so this plan does not do it.
- **Lifetime:** bound to the browser tab's session — cleared automatically when the tab closes (native `sessionStorage` behavior). This is the "browser-lifetime boundary" the task asks the plan to select.
- **Reload:** same-tab reload preserves `sessionStorage`, so the credential (uuid/secret) survives reload — but the message cursor does not, by design. On script load, if a stored conversation is found, the client issues one **hydration poll** at `since_id=0` (§3), renders the full returned transcript once into a fresh, page-local dedup set, sets the in-memory cursor to the highest `id` returned, then resumes normal 3s polling from that cursor. No message text is ever persisted to `sessionStorage` merely to make reload work.
- **Cross-tab:** none. A second tab has empty `sessionStorage` and starts an independent conversation on its own first send. This is a deliberate simplification (no BroadcastChannel/localStorage sync) appropriate to the lightweight scope.
- **Clearing:** on (a) explicit visitor "End conversation" action, (b) a `404` from `/messages` or the poll endpoint (secret invalid — see §6), or (c) conversation `status` returned as `resolved`/`archived` by poll. In all three cases this is **local client-state clearing only** — no M05 endpoint is called to end/archive/revoke; M05 has no such client-facing operation (ADR-0021: revocation happens server-side via retention/topic-resolution, never triggered by the client).
- **Secret transport:** the secret is client-generated (§0) and lives only in `sessionStorage`, read into memory to set a request header — `X-Universal-Telegram-Conversation-Secret` for the one-time start exchange, `Authorization: Bearer <secret>` for every subsequent message-post/poll request. It is never placed in a URL, query string, DOM attribute, `console.log`, or any static/cached HTML — this is enforced by using a JSON data island for *server-authored* config only (§4), which never contains a secret since it is never server-derived at any point in this protocol.

## 3. REST client behavior

- **Retry policy depends on WP0.** WP0 is sequenced before WP4, so the client below is built directly against the idempotent contract. A single automatic retry of start/send is safe **only** because it replays the same idempotency key (and, for start, the same client-generated secret) — it is never a bare, unkeyed retry. If WP0 is not yet available at WP4 implementation time for any reason, WP4 must ship with **no automatic retry** for start/send (manual "Try again" only, generating a fresh key/secret pair each manual attempt) until WP0 lands. Poll retry/backoff is unaffected either way — it was already safe, since polling is naturally idempotent via `since_id` and does not create records.
- **Start:** called only on first explicit send if neither `utChatConversation` nor `utChatPendingStart` exists in `sessionStorage`. If `utChatConversation` exists, skip straight to Send. If `utChatPendingStart` exists (a reload interrupted a prior in-flight start), reuse its `idempotencyKey`/`secret` rather than generating new ones. Otherwise: generate a fresh `Idempotency-Key` and 256-bit secret (§0), write `utChatPendingStart = {idempotencyKey, secret}` to `sessionStorage` **before** dispatch, then `POST /conversations` with body `{}` and headers `Idempotency-Key`, `X-Universal-Telegram-Conversation-Secret` (never in the body, never in a `chat_profile` — single default destination per scope decision). On success (`200`, `{ok:true, conversation_uuid, secret}` — `secret` here is simply the value the client already holds, echoed back per §0 step 4) replace `utChatPendingStart` with `utChatConversation = {uuid: conversation_uuid, secret, startedAt}`, then immediately issue the message POST. On failure: `503` → unavailable state (destination-related, per §1), and `utChatPendingStart` is cleared (terminal, no conversation to resume toward); `400` → transient failure, no automatic retry (client/format error, not transient), `utChatPendingStart` is cleared; network error/`5xx` → **one automatic retry reusing the same `utChatPendingStart` entry unchanged**, then surface failure with a manual "Try again" control (which also reuses the same stored `idempotencyKey`/`secret` — never regenerates them while `utChatPendingStart` still holds a pending attempt).
- **Send:** `POST /conversations/{uuid}/messages`, `Content-Type: application/json`, `{text}`, `Idempotency-Key: <per-message key, generated and persisted before dispatch>`. `200 {ok:true}` → move message from "sending" to "sent" locally (optimistic UI already showed the text; see §5 for what "sent" can and cannot mean). `400` → local validation issue (e.g. exceeded `MAX_TEXT_CHARS`, enforced client-side first to avoid a wasted round-trip) — no retry. `404` → terminal: treat as revoked/gone, clear state, show ended state. `429`/`5xx`/network error → **one automatic retry replaying the same per-message `Idempotency-Key`**, then manual retry control (same key); the failed message stays visible marked "not sent" (never silently dropped, never retried indefinitely).
- **Hydration poll (reload/re-entry):** when a stored conversation is found on script load but no in-memory cursor exists yet (fresh page load), issue one poll at `since_id=0` before starting the normal cadence. Render every returned message once into a page-local `Set` of rendered ids (rebuilt fresh each page load — deterministic, never persisted), then set the in-memory cursor to the highest `id` in that response and switch to the normal 3s cadence below.
- **Poll:** `GET /conversations/{uuid}?since_id=<cursor>` (cursor held in memory only, seeded either by the hydration poll above or by `0` for a same-page first poll), starts immediately after the first successful send (or after hydration), cadence 3s while the widget is open **and** `document.visibilityState === 'visible'`. Paused entirely (no requests) when the widget is closed or the tab is hidden; an immediate poll fires on re-opening or regaining visibility. Each poll cancels any still-in-flight previous poll via `AbortController` before issuing a new one (no overlapping requests). Backoff on transient failure: 3s → 6s → 12s → 30s cap, reset to 3s on the next success; `429` honors `Retry-After` if present, else applies the same backoff. `404` is terminal (§6). New messages are appended by `id` and added to the page-local dedup `Set`, which prevents duplicate rendering across overlapping/retried polls and across the hydration poll plus the first normal poll.
- **Cursor:** held only in memory for the page's lifetime (not persisted) — reload always re-derives it via the hydration poll, which is the deliberate mechanism for correct history rendering (see §2).
- **Cancellation:** all in-flight requests (start/send/poll) are aborted when the widget is closed or the page unloads, via `AbortController`, to avoid orphaned network activity and console errors.

## 4. Security, privacy, CSP/cache compatibility

- **Config transport:** a static, non-executable **JSON data island** — `<script type="application/json" id="ut-chat-widget-config">…</script>` — read via `document.getElementById(...).textContent` and `JSON.parse`. This is **not** an inline *executable* script (`type="application/json"` is never parsed as JS by the browser regardless of CSP `script-src`), so it requires no `'unsafe-inline'` grant and is not a CSP compatibility risk — correcting the earlier draft's mischaracterization of `wp_add_inline_script` as CSP-compatible (it is not: that mechanism emits an executable inline `<script>` and does depend on a CSP nonce/hash or `'unsafe-inline'`).
  - **Exact encoding:** `wp_json_encode( $config, JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT )`. `JSON_HEX_TAG` escapes `<`/`>` to `<`/`>`, which is sufficient on its own to prevent a `</script>` breakout even inside a `<script>` element; the other three flags are added defensively since the config is emitted inside an HTML attribute-free `<script>` body.
  - **Exact emitter/hook:** a new method `ChatWidgetAssets::print_config()`, hooked to `wp_footer` at a priority **below** WordPress core's own footer-script printer (`wp_print_footer_scripts`, hooked to `wp_footer` at priority `20`) — e.g. priority `5` — so the config island is always present in the DOM before `chat-widget.js` (enqueued `in_footer => true`) executes. Only called when `ChatWidgetAssets::should_enqueue()` is true, i.e. it exists on the page if and only if the script does.
  - **Content guarantee:** the only keys ever placed in `$config` are `restUrl` (`rest_url('universal-telegram/v1')`) and `namespace` — both static, identical for every anonymous visitor and every conversation. No `conversation_uuid`, `secret`, `idempotency key`, or any value derived from a specific request is ever passed into `print_config()` — the method's input is a fixed array literal, not request-derived data, which is what makes the identical-across-requests/cache-safety property structurally guaranteed rather than just intended.
- **No per-visitor state in HTML:** the conversation `uuid`/`secret` only ever exist in a REST JSON response body and in `sessionStorage`; they are never interpolated into server-rendered markup, so cached HTML is identical regardless of visitor or conversation state.
- **XSS:** all message text (visitor-authored or Telegram-origin) is rendered via `textContent`/DOM text nodes only, never `innerHTML`, never a markdown/HTML parser. Only the widget's own static chrome (buttons, containers, labels) may use `innerHTML`, and only with fixed, hardcoded, non-interpolated markup set once at init.
- **Origin/nonce:** the three M05 routes use `permission_callback => '__return_true'` (ADR-0019 pattern) — no WordPress nonce is available or expected client-side; this matches the existing visitor-ingestion precedent and requires no new client-side nonce handling.
- **No-store/no-CORS:** per ADR-0021 the REST responses already carry `no-store`; the widget adds no caching of its own for these responses (fetch default, no `cache:` override needed beyond relying on server headers).

## 5. Accessibility and responsive UX

- Toggle button: `<button aria-expanded>`, accessible name "Open chat"/"Close chat" toggled with state; keyboard-operable (native `<button>`, no custom key handling needed for activation).
- The panel is a **modal dialog** while open (focus is trapped within it, per below), so it carries `role="dialog"`, `aria-modal="true"`, and `aria-labelledby` pointing at a visible panel heading (e.g. "Chat"). On open: focus moves to the message input; `Escape` closes and returns focus to the toggle button; focus is trapped within the panel while open (Tab/Shift+Tab cycle within it, per standard dialog pattern — first/last focusable elements wrap).
- Message list: `role="log"` with `aria-live="polite"` so new operator messages are announced without interrupting; the visitor's own sent messages are not re-announced (appended to the DOM before the live region "settles," matching standard log-region practice).
- Contrast: CSS custom properties for widget colors, set to WCAG AA contrast ratios against both the widget's own background and typical page backgrounds (fixed values now — no live-preview editor, per scope decision).
- `prefers-reduced-motion: reduce` disables the open/close transition (swap to an instant show/hide); no motion is essential to functionality.
- **Mobile non-obstruction (testable strategy, not a vague "never covers" claim):** below a `600px` viewport-width breakpoint the panel becomes a bottom sheet with `position: fixed`, `max-height: min(70vh, calc(100% - 4rem))`, and `padding-bottom: env(safe-area-inset-bottom)`. A close control is **always rendered in a sticky, non-scrolling header row** at the top of the panel (never depends on scroll position to be reachable). Because there is no jsdom/browser test runner in this repo (§9), non-obstruction is verified by a **repeatable manual check**, not an automated assertion: at two fixed viewport widths (375px and 414px, both common WooCommerce mobile breakpoints), confirm the open panel does not overlap the theme's add-to-cart button or the WooCommerce mini-cart/checkout button, and confirm the close control is reachable and tappable without scrolling. This manual step is executed once, alongside the real-bot smoke test (§7) and the WP7 gate (§9).

## 6. Lifecycle and availability — exact state model

M05's poll response exposes only `{ok, status, messages:[{id, direction, text, created_at}]}` and `status()` is one of `open|resolved|archived` (`ConversationStatus.php`). **`delivery_state` (`stored|sent|failed`) exists on the message model but is never included in the poll payload** (`ConversationsController.php` poll mapping, lines ~296-308) — the widget therefore has **no visibility into whether a message actually reached Telegram**, and this plan does not invent a "delivered to operator" indicator. States are named honestly around what's actually observable:

| State | Trigger | Observable basis |
|---|---|---|
| **closed** | widget collapsed | client-only, no requests |
| **idle** | open, no conversation yet | empty `sessionStorage` |
| **sending** | first send in flight (start+post, or post only if already started) | request in flight |
| **active** | ≥1 message exchanged, polling live | `status: 'open'`, successful sends/polls |
| **unavailable** | disabled, no eligible destination, or `503` from start | `ChatWidgetAvailability`/HTTP 503 |
| **transient failure** | a single request failed (network/`429`/`5xx`) | HTTP-level, retryable, does not end the conversation |
| **ended/revoked** | `status ∈ {resolved, archived}` from poll, or `404` from post/poll | exact M05 fields — no invented "topic-creation pending" or per-message delivery-failure UI |

- Conversation starts **only on first explicit send** (privacy-minimal — no `/conversations` call merely from opening the widget).
- "End conversation" is a visitor-facing button that **only clears local `sessionStorage` and stops polling** — it does not call any M05 endpoint (none exists for this); the server-side conversation is unaffected and will resolve/archive on its own per M05's existing lifecycle. A subsequent send starts an entirely new conversation.
- Reaching `ended/revoked` (from either signal) clears `sessionStorage` and shows a dismissible "conversation ended" notice with a "Start a new conversation" control.

### ADR-0022: Chat Widget Client-Side State and Cache-Safe Configuration

**Status:** Proposed

**Context:** M05 (ADR-0021) defines a bearer-secret visitor credential with no client-facing rotation/reissue/revocation endpoint — a `404` on post/poll is terminal. M06 must hold this secret in the browser across a visitor's interaction without introducing cookies, cross-site identity, or any secret/per-visitor data in server-rendered (and therefore cacheable) HTML.

**Decision:** The widget stores conversation state (`conversation_uuid`, `secret`, start time) exclusively in `sessionStorage`, under key `utChatConversation` (with a transient `utChatPendingStart` entry while a start request is in flight — see the ADR-0021 amendment for that protocol), scoped to the browser tab's session lifetime. The message cursor is held only in memory and re-derived on each fresh page load via a hydration poll, so no message content or cursor is ever persisted to `sessionStorage`. Once a conversation exists, the secret is attached only as a `fetch` `Authorization: Bearer` header for message-post/poll requests, never in a URL or DOM attribute; during the one-time start exchange it is instead sent as `X-Universal-Telegram-Conversation-Secret`, per the ADR-0021 amendment. Server-rendered configuration (REST base URL/namespace only, identical for all visitors) is emitted as a static `<script type="application/json">` data island, never as an executable inline script and never containing any per-visitor value. A `404` from any authenticated route, or a `resolved`/`archived` conversation `status`, is treated as terminal: the client clears its local state and requires a new conversation on next send. Ending a conversation from the widget clears local state only and calls no M05 endpoint, since none exists for client-initiated termination.

**Consequences:** Each browser tab holds at most one independent, non-recoverable conversation; there is no cross-tab sync and no persistence beyond the tab's session, which matches M05's no-reissue guarantee and keeps the secret's blast radius bounded. Full-page caching is unaffected because no per-visitor value is ever written into cacheable HTML. Reload history is served by a from-scratch hydration poll rather than a persisted transcript, keeping stored client state minimal. A future milestone introducing token rotation or multi-tab continuity would need to revisit this ADR.

### ADR-0021 Amendment: Idempotency-Key Support for Start and Message Endpoints

**Status:** Proposed addendum to ADR-0021.

**Context:** M06's chat widget must be able to safely retry `POST /conversations` and `POST /messages` after a network or `5xx` failure. ADR-0021 as written has no notion of a client-supplied idempotency key, so a naive client-side retry risks creating a duplicate conversation or duplicate message. Additionally, ADR-0021's existing flow generates the bearer secret server-side and returns it once; a safe start-replay requires the server to be able to verify a resend of that same secret without ever storing more than a hash of it.

**Decision — start (`POST /conversations`):** the client now generates **both** the `Idempotency-Key` and the 256-bit bearer secret itself, before dispatch, and sends them as two request headers — `Idempotency-Key` and `X-Universal-Telegram-Conversation-Secret` — never in the body, a URL, or any logged/cached location. On an unseen `Idempotency-Key`, the server validates the secret's format (64 lowercase hex characters), creates the conversation row storing `password_hash(secret)` (via `password_hash()`, as today) and the unique `start_idempotency_key`, and returns `{ok:true, conversation_uuid, secret}` where `secret` is simply the value the caller supplied. On a replay with the same `Idempotency-Key`, the server looks up the conversation by that key, verifies the supplied secret via `password_verify()` against the stored hash, and — on a match — returns the identical response shape without creating a second row. A replay with a missing or incorrect secret returns the same generic `400` failure shape used for any other malformed start request, so no information about the key's existence or the correct secret leaks. The server **never** persists the secret itself, encrypted or otherwise — only its hash, exactly as ADR-0021 already specifies for the non-replay path.

**Decision — message (`POST /conversations/{uuid}/messages`):** unchanged from a plain idempotency-key addition: accepts an `Idempotency-Key` header, persisted scoped to `(conversation_id, idempotency_key)` (unique index); a replay with the same key returns the original message's success response rather than inserting a duplicate row.

**Schema:** both columns are added to the two existing M05 tables — no new table — via one new `Migrator` step (`step_13_add_conversation_idempotency_columns()`), advancing `db_version` from `12` to `13`: `universal_telegram_conversations.start_idempotency_key CHAR(36) NULL` with a unique key, and `universal_telegram_conversation_messages.idempotency_key CHAR(36) NULL` with a unique key on `(conversation_id, idempotency_key)`. Both are nullable specifically so pre-migration rows require no backfill (unique indexes permit multiple `NULL`s), making the upgrade path safe for existing installations.

**Retention:** both the `start_idempotency_key` column and the per-message idempotency key are retained only as long as the row they are attached to, using the same retention/cleanup path ADR-0021 already defines — no separate cleanup logic, since the columns are deleted along with their row. Neither key is ever included in poll responses.

**Consequences:** M06 (and any future client) can safely implement bounded automatic retry for both endpoints, using a key the client already holds rather than one the server must return and the client must remember. This is a backend schema/logic change to the Conversations boundary (`db_version 12 → 13` migration adding the two columns/unique indexes, plus a `password_verify`-based replay branch in the start handler and a replay branch in the message handler) and must ship before any client relies on automatic retry of these routes.
