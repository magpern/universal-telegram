# Architecture Reference

This document records the plugin's thirteen authoritative product boundaries and the versioning conventions established by the M00 plan (`docs/plans/m00-product-foundation-plan-v1.md`, section 4.1 and section 9). It is the canonical source of truth for boundary ownership; a structural guard test (`tests/unit/Core/StructuralBoundariesTest.php`, added if and when a later milestone needs one — see below) enforces the continued absence of an unimplemented boundary's directory until its own owning milestone's frozen plan authorizes creating it.

| 7 | Automations | `UniversalTelegram\Automations` | Implemented at M02 (notification rule storage, deterministic evaluation, message templates, idempotent dispatch log, rule simulation); M08.1 (ADR-0032) extends condition evaluation from AND-only to an explicit per-rule `match_mode` (`all`/`any`, defaulting to `all`) and adds three fixed comparison operators, still a flat, non-nested, closed-grammar clause array; digests and operational intelligence (M11) are a subdomain of this boundary — the `Automations\Digest` subdomain (M11A, ADR-0029: scheduled visitor-activity digests, threshold/timeout batching) and the `Automations\Intelligence` subdomain (M11B, ADR-0030: scheduled operational summaries, threshold alerts, funnel/error-clustering aggregates, operator-triggered AI-assisted internal summarization reusing M09's provider abstraction and site-wide concurrency cap) |

| 9 | Conversations | `UniversalTelegram\Conversations` | Implemented at M05 (ADR-0021): conversation/message persistence, bearer-secret visitor authentication, the public start/post/poll REST contract, idempotent Telegram forum-topic creation, visitor-to-Telegram outbound routing, topic-scoped inbound reply capture, and fixed-default retention cleanup); operator workflow (M07, ADR-0026) and conversation topic lifecycle / remote forum-topic deletion (M07.1, ADR-0031) are subdomains of this boundary. **Legacy runtime until Support Chat SC-M03.** Chat-experience follow-ons M05.2 / M07.2 (ADR-0033–0035) were documentation-only and are **superseded for UT implementation** by ADR-0037 (requirements rehomed to Universal Support Chat + optional UT Adapter M1). |
| 10 | ChatWidget | `UniversalTelegram\ChatWidget` | Core slice implemented at M06 (ADR-0021 amendment, ADR-0022): availability gating, cache-safe asset enqueue, and the visitor-facing widget consuming M05's REST contract only. M06.3.1 (ADR-0025) replaces the visitor-entered name with an authenticated-only access model: sign-in-gated widget state, server-derived display name, persistent conversation ownership, a database-enforced one-active-conversation-per-owner-per-bot guarantee, explicit cookie+nonce CSRF enforcement additive to the existing bearer secret, cross-session resume, and a new `theme` default preset using generic WordPress/WooCommerce CSS-variable fallback chains; chat profiles/targeting, business hours, pre-chat form, a custom-CSS editor, and page-builder embeds remain deferred, unscheduled charter items. **Legacy runtime until SC-M03.** Planned M06.4 was docs-only and is **superseded for UT implementation** (ADR-0037; rehomed to Support Chat SC-M05). |
| 11 | AI | `UniversalTelegram\AI` | Implemented at M09 (ADR-0028): operator-assist-only draft generation — provider abstraction with a single OpenAI adapter, disabled by default; explicit per-conversation visitor acknowledgement gate; source-only retrieval from explicitly approved published content; a bounded, lease-recovered, concurrency-capped draft lifecycle; and a fixed six-class structural allow-list preventing any automatic customer/Telegram delivery. `AI\Provider\ProviderConcurrencyGate` (M11B, ADR-0030) extends the site-wide provider-concurrency admission mutex to be shared across M09's AI draft assistant and M11B's operational-summary AI generation, without adding any class to the six-class allow-list. **Historical/legacy until Support Chat SC-AI1.** Planned M09.1 (ADR-0036) and M10 UT paths are **superseded for UT implementation** (ADR-0037; rehomed to Support Chat SC-AI1 / SC-AI2). |
| 12 | Administration | `UniversalTelegram\Administration` | Implemented (`Diagnostics` at M00; the `Telegram` subdomain — bot/destination management screen and request handling — added at M01; the `Automations` subdomain — event catalog, rule builder, rule tester, and event history browser — added at M02; the `Hub` subdomain — single top-level menu entry, URL-driven tab registry/shell, and legacy-URL compatibility redirects, superseding per-screen `add_submenu_page()` calls as the boundary's default administration-screen pattern — added at M04.1, ADR-0020). M08.1 (ADR-0032) replaces the `Automations\RuleBuilderPage` raw event-type/JSON-conditions form with a preset-card, friendly-picker, visual condition-row Add Rule flow inside the existing `rules` Hub tab — no new Hub tab is added. M08.2 replaces the developer-oriented `Automations\RuleSimulatorPage` with `Administration\Automations\NotificationTesterPage` (no-dispatch, no-persistence rule/event testing reusing M08.1's friendly-metadata catalogs) and regroups the Hub's flat top-level tab row into seven grouped areas via a new `Hub\AreaPage`, each area listing its own existing screens as an accessible secondary tab row — a presentation/navigation change only, every legacy direct tab URL still resolves via `Hub\HubPage::LEGACY_TAB_ALIASES` |
| 13 | Integrations | `UniversalTelegram\Integrations` | Implemented (the `WooCommerce` subdomain, presence detection only) |

`Security`, `Configuration`, and `Lifecycle` are internal components of the `Core` boundary, not boundaries of their own. `Diagnostics` is an internal subdomain of `Administration`. No later milestone should introduce a new top-level boundary beyond these thirteen; a genuinely new product concern is placed as a subdomain of the closest-fitting existing boundary, or requires its own architecture decision superseding this one if none fits.

## Support Chat extraction (ADR-0037)

Website support chat is extracted to standalone **Universal Support Chat**. This plugin remains responsible for Telegram transport, bots/destinations/webhooks/commands, event/WooCommerce/error notifications, and an optional Support Chat adapter (UT Adapter M1).

- ADR-0033–0036 are **Superseded by ADR-0037** for future UT chat-product implementation direction; historical ADR bodies are preserved.
- M05.2 / M06.4 / M07.2 / M09.1 / M10 are **not authorised for implementation** in Universal Telegram; requirements are rehomed to Support Chat milestones.
- **No M05.2 code was implemented.** Empty branch `feature/m05-2-escalation-aware-routing` may be deleted only after the supersession documentation amendment merges.
- Legacy Conversations / ChatWidget / Hub conversation admin / M09 AI draft runtime remains until Support Chat SC-M03 (and SC-AI1 for AI drafts) — this documentation does not extract or disable that code.
- Canonical Contract v1 lives only in Support Chat; pin:
  - SHA `dff2730e24b7d3f70f15f706305e12e14fdcc6c8`
  - URL `https://github.com/magpern/universal-support-chat/blob/dff2730e24b7d3f70f15f706305e12e14fdcc6c8/docs/adr/0005-canonical-support-channel-contract-v1.md`
- **Contract v1 authentication (ADR-0038, pinning Support Chat ADR-0007):** UT Adapter M1's `SupportChatContractClient` and `OutboundContractController` now perform real mutual Ed25519 request signing/verification, auth profile `support-channel-contract-auth/v1` — pinned to Support Chat commit `8ee396d8b8edcbf526797c0a1f5741f3842df57a`: `https://github.com/magpern/universal-support-chat/blob/8ee396d8b8edcbf526797c0a1f5741f3842df57a/docs/adr/0007-contract-v1-mutual-signed-adapter-authentication-profile.md`. Implemented, tested, and proven via a joint interoperability gate against a live Support Chat authenticated Contract server (PR #34, PR #35).
- **Legacy export boundary (ADR-0039, pinning Support Chat ADR-0008):** Support Chat's SC-M03 legacy migration engine (work packages 3–4) requires a narrow, versioned, in-process, WP-CLI-only export interface from this plugin, `LegacyExportServiceV1` — pinned to Support Chat commit `7546d43be66f8e3b2f179f03a1c81c9aadef59db`: `https://github.com/magpern/universal-support-chat/blob/7546d43be66f8e3b2f179f03a1c81c9aadef59db/docs/adr/0008-legacy-export-boundary-and-migration-authority-model.md`. Implemented (`src/SupportChatAdapter/Migration/LegacyExportServiceV1.php`), Product Owner acceptance pending.
- **Legacy binding preparation boundary (ADR-0041, pinning Support Chat ADR-0009):** Support Chat's SC-M03 work package 5 requires a narrow, versioned, in-process, WP-CLI-only binding-write interface from this plugin, `LegacyBindingImportServiceV1`, a new non-routing `prepared` binding status, and a lock-scoped quiescence assertion — pinned to Support Chat commit `590b53ba898aa4054ec65c65965c152a3612149b`: `https://github.com/magpern/universal-support-chat/blob/590b53ba898aa4054ec65c65965c152a3612149b/docs/adr/0009-legacy-binding-preparation-boundary-and-non-routing-prepared-status.md`. ## Versioning conventions

The plugin's version, held in the `UNIVERSAL_TELEGRAM_VERSION` constant and mirrored in `readme.txt`'s own stable-tag field, moved from `0.0.1` (M00) to `0.1.0` (M01) to `0.2.0` (M02) to `0.3.0` (M04) — each a minor bump, since each milestone is a genuine new functional-capability class rather than a patch-level fix. M03 did not bump the version: it is additive registrations against the existing event system, not a new top-level capability class. M04.1 moved `0.3.0` to `0.3.1` — a patch bump, not a minor one, since it introduces no new end-user functional capability and no persistence change: it is a pure administration-navigation restructuring (single Hub menu entry, URL-driven tabs, ADR-0020) over screens and capabilities that already existed. M05 moved `0.3.1` to `0.4.0` — a minor bump: the conversation backend (ADR-0021) is a genuine new functional-capability class, with a new persistence model and public REST contract. M06 core moved `0.4.0` to `0.5.0` — a minor bump: the chat widget (ChatWidget boundary, ADR-0021 amendment, ADR-0022) is a genuine new functional-capability class, with its own new REST-client-facing frontend and a schema change. M06.1 moved `0.5.0` to `0.6.0` (bot setup wizard). M06.2 moved `0.6.0` to `0.6.1` — a patch bump, not a minor one, since it introduces no new end-user functional capability and no persistence change: expedited interactive queue dispatch (ADR-0023) and a bounded synchronous administrator Test Message are a latency and diagnostics improvement over the existing Conversations/ChatWidget and Telegram Administration capabilities, not a new capability class, mirroring the M04.1 precedent. M06.2's own corrective pass (v2, ADR-0023 amendment) moved `0.6.1` to `0.6.2` — also a patch bump: replacing the primary latency mechanism, adding the claim/lease schema change, and correcting the widget/rate-limit interaction all remain reliability fixes to the same already-shipped capability, not a new one. M06.3 (ADR-0024) moved `0.6.2` to `0.7.0` — a minor bump: required visitor display-name persistence plus a new presentation/style-preset system together constitute a genuine new functional-capability class, not a patch-scale fix, mirroring the M06-core `0.4.0` → `0.5.0` precedent. M06.3.1 (ADR-0025) moved `0.7.0` to `0.8.0` — a minor bump: mandatory WordPress authentication, persistent conversation ownership, a database-enforced concurrency guarantee, and an explicit CSRF boundary together replace the prior access model with a genuinely new capability class, not a patch-scale correction, correcting the Product-Owner-rejected M06.3 onboarding design. M07 (ADR-0026) moved `0.8.1` to
`0.9.0` — a minor bump: identity-gated inbound Telegram operator authorization, operator presence/
unread state, an operator inbox and detail view, concurrency-safe assignment, a reopen transition,
archived-only manual deletion via a shared purge service, and bounded conversation search together
constitute a genuine new functional-capability class, not a patch-scale fix. M08 (ADR-0027) moved
`0.9.0` to `0.10.0` — a minor bump: a fixed, allow-listed administrative-bot command surface (entity-
based recognition, two-factor operator authorization, bounded read-only WooCommerce queries, and
confirmation-gated `/resolve`/`/reopen` transitions) is a genuine new functional-capability class,
with no schema change (`db_version` unchanged). M09 (ADR-0028) moved `0.10.0` to `0.11.0` — a minor
bump: the operator-assist-only AI draft assistant is a genuine new functional-capability class, with
a schema change (`db_version` 18→21, plus a corrective step to 22). A subsequent corrective patch
(fix/ai-model-dropdown-and-checkbox-save-bug) moved `0.11.0` to `0.11.1` — a patch bump: a
settings-checkbox-save bug fix and the removal of the developer-only click-tracking controls, with no
new functional capability and no schema change. M11A (ADR-0029, the non-AI first slice of M11) moved
`0.11.1` to `0.12.0` — a minor bump: scheduled visitor-activity digests with administrator-configurable
threshold/max-wait batching are a genuine new functional-capability class, with a schema change
(`db_version` 22→24). M11B (ADR-0030, completing M11 together with M11A as one combined release) moved
`0.12.0` to `0.13.0` — a minor bump: scheduled operational summaries, threshold alerts, funnel/error-
clustering aggregates, and operator-triggered AI-assisted internal summarization together are a genuine
new functional-capability class, with a schema change (`db_version` 24→28). M11A is not independently
released; both `0.12.0` and `0.13.0` are recorded here for lineage, but the combined M11 milestone
closes citing this final `0.13.0`/`db_version` 28 state. M07.1 (ADR-0031, on the combined M11
branch) moved `0.13.0` to `0.14.0` — a minor bump: conversation topic lifecycle (local Archive,
confirmation-gated queued remote forum-topic deletion for eligible plugin-created topics only,
topic-unavailable repair, exclusive destination ownership, and truthful visitor delivery states)
is a genuine new functional-capability class, with a schema change (`db_version` 28→29). Combined
implementation is on `main` at `0.14.0` / `db_version` 29; the CI-repair and full validation gate
are closed (see `docs/closure/m11-m07-1-ci-repair-and-validation-gate-closure.md`). M08.1 (ADR-0032)
moved `0.14.0` to `0.15.0` — a minor bump: the friendly rule builder and notification presets
(preset-card picker, visual condition builder, plain-language message editor with field-insert and
preview) are a genuine new functional-capability class, with a schema change (`db_version` 29→30,
one additional migration step adding the per-rule `match_mode` column). M08.2 moved `0.15.0` to
`0.16.0` — a minor bump: the friendly "Test notifications" tab (replacing the developer-oriented
Simulator with existing-notification and custom-scenario testing modes, plain-language would-send/
would-not-send results, and a guaranteed no-dispatch, no-persistence evaluation path) together with
the grouped seven-area Hub navigation (superseding the flat top-level tab row, full legacy-URL
compatibility preserved) are a genuine new functional-capability class, with no schema change
(`db_version` unchanged at 30). Product Owner acceptance, tag, release ZIP, and deployment remain
pending — this version is recorded for lineage, not as a released or accepted milestone.
Versioning follows Semantic Versioning: while the plugin remains below `1.0.0`, any of the minor or patch positions may introduce a breaking change without a major-version bump. Version `1.0.0` is reserved for the release completing milestones M00 through M07 together with M12; major-version bumps after that point are reserved for breaking changes to the plugin's own public contracts, once any exist.

The database schema version is an entirely independent, monotonically increasing integer, unrelated to the plugin's own Semantic Versioning string, stored in its own dedicated option (`universal_telegram_db_version`), starting at `1` for M00's own single migration step, moving to `7` at M01 (six additional Telegram tables), to `10` at M02 (three additional migration steps: `event_history` and `fatal_error_markers` at step 8, `notification_rules` at step 9, `notification_dispatch_log` at step 10), to `12` at M05 (two additional migration steps: `universal_telegram_conversations` at step 11, `universal_telegram_conversation_messages` at step 12), and to `13` at M06 core (one additional migration step, `step_13_add_conversation_idempotency_columns`, altering — not adding — those same two M05 tables with nullable, uniquely-indexed idempotency columns), and to `14` at M06.2's own corrective pass (v2, ADR-0023 amendment; one additional migration step, `step_14_add_claim_lease_columns`, adding nullable `claim_expires_at`/`topic_claim_expires_at` lease columns to the outbound messages and conversations tables, powering the claim-protected delivery protocol), and to `18` at M07 (two additional migration steps: `universal_telegram_operator_identities`, `universal_telegram_conversation_notes`, and `universal_telegram_operator_availability` at step 17, and `assignee_last_seen_message_id`/`telegram_sender_user_id` columns added to the conversations/conversation-messages tables at step 18), and to `22` at M09 (ADR-0028; `universal_telegram_ai_config` at step 19, `universal_telegram_ai_drafts` at step 20, a nullable `ai_ack_policy_version` column added to conversations at step 21, and a corrective step 22 widening `ai_drafts.requested_by_user_id` to nullable), and to `24` at M11A (ADR-0029; two additional migration steps: `universal_telegram_visitor_digest_counters` at step 23 and the seeded singleton `universal_telegram_visitor_digest_state` at step 24), and to `28` at M11B (ADR-0030; four additional migration steps: `universal_telegram_operational_summary_runs` at step 25, the seeded singleton `universal_telegram_intelligence_settings_state` at step 26, `universal_telegram_operational_alert_state` seeded with its three fixed alert-type rows at step 27, and `universal_telegram_operational_summary_ai_drafts` at step 28), and to `29` at M07.1 (ADR-0031; one additional migration step: topic lifecycle columns plus UNIQUE `conversations.destination_id` after duplicate-nulling repair), and to `30` at M08.1 (ADR-0032; one additional migration step, `step_30_add_notification_rule_match_mode_column`, adding the per-rule `match_mode` column). M08.2 adds no migration step; `db_version` stays `30`.

A future Git tag, whenever one is first created by whichever milestone first produces a public release, follows the format `vX.Y.Z`. A built distributable package is named `universal-telegram-{version}.zip`, built via `bin/docker/build-zip.sh`. No Git tag and no GitHub Release exist as of M02.
